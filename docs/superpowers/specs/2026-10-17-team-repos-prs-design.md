# Team repositories, pull requests and owner PR work

Date: 2026-10-17. Status: proposed; owner recommendations support planning, not activation.

## Intent and boundaries

Solo repositories (motif, drover, PanGloss) keep local fast-forward delivery and push off by default. Team repositories (machine = `sillsdev/machine`, FieldWorks) deliver through GitHub PRs; only a confirmed human-controlled merge completes their implementation tasks. Types, fields, states and forms are T-9 configuration; code supplies bounded GitHub effects, evidence and permission enforcement.

Deliverables are this design, its implementation plan and hub task JSON. No product code, repo registration, dependency installation, GitHub mutation or live policy change is authorized here. No public webhook endpoint or new service is required. Fork PRs may be reviewed, but publishing fixes to a fork is deferred until an owner explicitly registers its head repository and grants access. No automatic merge, force push, shared-branch rewrite or automatic branch deletion.

## Options and selected approach

1. **Recommended: T9 definitions plus one hub GitHub adapter and durable PR projection.** Extend the constrained effect vocabulary; retain separate local delivery. Fits existing authority/outbox and keeps YAML declarative.
2. Give workers authenticated gh and teach each skill to post: less hub work, but weak approval recovery, duplicated polling and broad credentials. Reject.
3. Replace all delivery with GitHub or an arbitrary workflow engine: simplifies one path while changing solo behavior and increasing migration scope. Reject.

## Repository configuration and onboarding

Names do not imply mode. `landing.mode` defaults to local for solo, pr for team; conflicting explicit combinations fail. Solo keeps existing explicit legacy push=true behavior; new registrations default false. Team requires `landing.push=false` (this legacy flag always means main push); its approved branch pushes are a separate effect. Never reinterpret an existing true value as branch-push consent.

## Delivery kernel and lifecycles

Extend T9, explicitly, in these ways (E13/E14): `sync` declares `executor: github-sync` (one core allowlisted value) and no LLM routing; new bounded actions `observe-pr`, `draft-publication`, `publish-approved`; new delivery modes `github-pr` for primary team code and `pr-update` for auxiliary response rounds. These are core capabilities, never arbitrary YAML hooks. Resolved team implementation/fix/docs/spec types use github-pr when their original delivery changes the repository, retaining spec-only path restrictions; no-repo types retain artifact delivery. Solo snapshots do not change.

`team-pr-v1` states/phases: proposed(pending) → ready(eligible, owner approval) → claimed → running → prepared(running, scoped commit recorded) → publication-pending(waiting-owner) → pr-open(running) → checks-passed(gated) → awaiting-merge(reviewed) → landed(completed). pr-open through awaiting-merge are service-managed, with no model seat or worker lease; phase alone must not launch a worker. Optional local gate and optional agent review precede publication as independent evidence; remote CI is the primary gate, and human review satisfies the review requirement. Required T9 local high-risk/task minima still run before publish. States and their guards/actions live in YAML; dispatcher uses capabilities and action IDs rather than type/state-name switches.

Any external-wait state may acquire owner holds, move to needs-owner(waiting-owner) or blocked, and retry with current approval; retain resume intent and recompute live guards. Pending CI stays pr-open without hot worker retries. Red CI opens proposed fix/response work and records the failure; new review comments create deduplicated response/conflict owner work. A new head invalidates prior head-bound CI/review/publication/merge approvals, returning to pr-open; base/rule changes invalidate the relevant readiness evidence. Closed unmerged → closed-unmerged(cancelled), unsuccessful. Cancellation stops publication and releases reservations only after safe local cleanup; monitoring may retain external history without reopening the task. Reopened PR before terminal cancellation can resume; after terminal cancellation create proposed continuation, never mutate a terminal lifecycle snapshot.

`pr-action-v1` extends artifact-v1 with drafted(running), publication-pending(waiting-owner), published(completed). Completion requires artifact acceptance plus required effect receipts, not just worker exit. Open-pr completes when the PR exists at its expected head; review-pr completes when the approved review is reread on GitHub. `pr-update-v1` prepares a scoped commit, waits for push approval, verifies the non-force remote head and current required CI, then publishes individually approved replies and completes that round. It never writes task_landed or makes the parent implementation successful. Reply-only rounds require artifact plus reply receipts, with no fake commit/gate. Disputes/ambiguities wait for owner decisions; canceled/failed round tasks cannot unblock the parent as successful.

Scope reservation delegation is an explicit kernel addition: under owner approval, atomically suspend the parent's writer, delegate only its approved fix subset to one response child, and reserve the union against unrelated work. Child uses a new owned worktree/branch based on the observed PR head. No two writers share the PR branch, and no worker edits another task's worktree. After verified publication or safe canceled cleanup, transfer the reservation back to parent. Parent reservation remains until merge/cancel-safe cleanup; unrelated overlapping tasks wait. Only primary github-pr delivery requires final main-merge evidence; auxiliary pr-update success means the round is delivered, never code landed.

## Publication approval and recovery

Draft every outward effect, even in trusted mode. `PublicationDraft` contains ID/version, originating task/run, action, registered target repository/ref/PR/thread, expected head/base/remote-old SHA, payload (title/body/review event and inline positions or push commit range), policy/type versions, source artifact hash and deterministic action hash. No secrets. Show the exact text or commit diff/range, target, account binding and observed validation in web/CLI. PR text has a stable task marker for reconciliation. No invented test claims, personal paths or unnecessary private context in public bodies.

Default always-ask requires an authenticated owner action for each push, PR creation, submitted review and thread reply. Initial push and creation are two separately receipted effects with an owner preview of both; they may be approved together only if no invoked skill requires individual approval. Trusted-types records an audited policy authorization for an exact type hash/action allowlist; it still stores the draft and cannot include merge, force, delete, thread-resolution or protection changes. Skill requirements, explicit task restrictions and owner holds are stricter ceilings. Review skills requiring approval always request it. PR merge stays manual under repo rules in both modes.

Approval binds `(draft_hash, task_revision, type_version, repo_policy_hash, expected_head, expected_base, remote_old_sha, target IDs)` and owner identity/time. Immediately before mutation reread state, head/base and relevant target/comment/rules, validate hash/approval and cancel/hold state, and persist an outbox intent. Changed text, head/base, policy, target, scope or stale inline position invalidates approval with 409; never silently re-anchor a finding or carry an old approval onto new commits. Atomic remote operations use expected SHA/preconditions where supported; otherwise record the race window and reconcile, never claim a cross-system transaction. Read PR state immediately before posting and verify returned effect afterward; quarantine any race that could not be proved safe.

Hub-only executor publishes an explicit reviewed SHA with a single explicit destination ref. Validate ref syntax and refuse the configured default branch or any protected publish target. Before branch push, fetch the remote head and require expected-old equality plus ancestry; existing branch changes only by normal fast-forward push. No `--force`, `--force-with-lease`, implicit push defaults or rebase of a published shared branch. Races reject naturally; refresh and redraft on mismatch. Merge base into the isolated response branch only within approved scope; conflicts, unrelated changes, fork permissions or a foreign head advance create owner work. T-8 item 7 must supply owner-approved commit identity before publishing; check identity without inventing emails or rewriting history.

Outbox execution stores intent before network, then external IDs/URLs/content hashes. A crash after a write but before recording its result is ambiguous: reconcile by stable PR marker + head/base, review ID/body/commit, reply thread/body marker, or remote ref SHA. Exactly one matching effect → record receipt; no provable or multiple matches → needs-owner, no blind retry. Approval permits the exact intended effect, not an unlimited retry stream. Rejected mutation leaves other approved effects pending; resume revalidates each. Posts/replies never resolve or dismiss others' threads/reviews implicitly.

Repo-changing worker records may include bounded `pr_drafts` proposals alongside ready_to_commit/done; preserve them in runner/launch recovery (JSON list, ≤64 KiB UTF-8 total, known schema, no authority flags). They grant no permissions. Dispatcher binds proposals to the assigned run/task/head before storing; hub assigns IDs/hashes. No-repo workers keep T9 authenticated artifact upload/result receipts and put draft proposals in that artifact. Malformed proposals cannot silently disappear and lead to publication. This avoids granting workers owner credentials or widening T9 artifact-upload authority to repo-changing tasks.

## GitHub adapter, checks and polling

Use already installed authenticated **Windows gh**, invoked by the hub with argv/JSON stdin, fixed registered host/repo, timeouts and bounded output; never shell interpolation, cwd-derived repository selection or tokens in briefs. Onboarding probes that exact Windows account/executable: WSL gh authentication proves nothing about Windows. Workers may analyze immutable inputs without gh credentials. Missing Windows gh/auth/permissions → owner prerequisite; no install, token copying or WSL fallback with publishing rights.

`GitHubClient.read(...)` uses `gh api --method GET` explicitly for REST; GraphQL queries use a fixed query allowlist (its HTTP POST is read-only). Normalize PR identity/state/head/base, author_login, mergeable and unanswered_feedback (IDs, author kind, blocking flags and oldest unanswered timestamp; unknown history stays unknown), formal reviews, inline review threads, issue comments, check runs/status contexts, rules and merge metadata. Paginate every collection, including nested GraphQL connections. Use GraphQL for coherent PR/review/rule summaries and REST for individual comments/check detail where appropriate. Do not infer gate success from gh exit code or an empty `pr checks` list. `GitHubClient.mutate(...)` is reachable only from the approval executor. Direct REST/GraphQL HTTP clients are deferred: gh reuses installed auth and needs no new Python dependency; isolate transport for later replacement.

Remote gate evidence binds host/repo/PR, head and base SHA, requirements/rules hash, fetched-at, per-check external ID/context/app and state/conclusion/link; merge-queue runs also bind their tested group SHA and server membership. Required set = discoverable applicable repo requirements union configured extra contexts. Passing means every required check has a current accepted conclusion for its tested revision, with GitHub rule semantics for neutral/skipped and app attribution; unknown/waiting/missing/canceled/stale/ambiguous requirements never mean pass. Empty set needs explicit `allow_no_required_checks` approval and a recorded no-required-checks exemption. Inaccessible rules → unknown/needs-owner evidence confirmation, not empty requirements. Human approval must be current, eligible and not dismissed/stale, respect required counts/code owners/request-changes rules, and include at least one non-agent human approval by default. Optional agent LAND cannot substitute. Draft PR, unresolved required threads, unknown mergeability, failing checks or rule conflicts prevent merge-ready.

GitHub enforces its rules when people merge. Polling is advisory readiness, never permission to bypass or choose an unsupported merge method. Merge queue is human-controlled too; observe queued status and applicable group checks, wait for actual merge. Record actual merge SHA and merged_at from GitHub; squash/rebase merge SHA may differ from the task head. Receipt records both, never asserts equality or copies a local batch gate onto the merge commit. If a merge is observed before required evidence can be verified, persist merged fact but hold primary task in merged-unverified(blocked) with owner work; complete only after verified rule/evidence reconciliation. No fabricated CI or reviewer receipt.

No webhook listener. A bounded tick (at most every 5s, no new thread/service, separate deadline preserving the existing 120s solo landing cadence) in the existing hub scheduler coalesces all tasks linked to a PR into one observation. Recommended intervals: active 30s, idle 120s, dormant 600s with ±20% jitter; persisted exponential failure backoff caps at 30m. Observation may continue while dispatch/publication is paused under its saved monitoring approval; pause never authorizes a write. Successful terminal observations stop normal polling; explicit refresh is rate-limited and never clears a host backoff. Persist host credential budget/reset, endpoint ETag/Last-Modified where supported, per-PR next_poll_at/cursors/errors. Honor Retry-After, rate reset and secondary-limit signals; do not hardcode a quota. Budget exhaustion postpones reads/writes and warns once, not a task failure/requeue storm. Auth/permission failures deduplicate owner tasks; transient outage keeps last good snapshot visibly stale and never advances completion.

For each poll, read beginning identity/head, all pages, then ending identity/head; accept only a coherent generation. Re-read base/rules for readiness decisions. Persist snapshot/events/watermarks transactionally after all pages succeed; failure leaves old watermarks. Stable `(external_id, updated_at, content_hash)` observations deduplicate retries while preserving edits/deletions as history; do periodic full reconciliation to catch resolved threads and closed/reopened state. Polling cannot recover every transient event between polls: ledger records observations, not a claim to mirror GitHub's entire audit log. Never mark a timeout/404 as closed or merged.

Owner answer completion authorizes its specific draft/decision and removes only its hold. No fake worker run for polling or owner actions.
