# CI-parity local gates, triage, review and landing

Date: 2026-10-19. Task: T-ce. Status: proposed implementation contract; owner decisions G1–G7 are approved. This document authorizes no live configuration changes, installs, services, publication or merges.

## Intent and decisions

Drover should spend compute proving a candidate and spend model tokens where judgement helps. For solo repos, derive build and test gates from GitHub workflows and execute them locally, without GitHub or an agent executing the gate. The Windows host and the registered WSL Ubuntu distro are the CI environments. Docker images and a general GitHub Actions emulator are future work.

| Decision | Required behavior |
| --- | --- |
| G1: local CI parity | Derive the same required build/test jobs, matrix variants and prerequisites from workflows. Map Windows jobs to Windows and Ubuntu jobs to WSL. Report every unsupported obligation and environment difference; never call a partial check full parity. |
| G2: mechanical green landing | Docs-only and mechanical tasks skip agent review. Reuse valid review evidence for land-candidates. New agent-written code receives one Sol review before landing; HOLD fixes receive focused re-review, without another review merely for entering the landing queue. |
| G3: cheap failure triage | Luna or Haiku sees a bounded failing excerpt first. It proposes flaky, environment/sandbox, already failing on main, or change-caused routing. Deterministic validation controls the action. Only change-caused failures go back to the worker, with at most ten summary lines. |
| G4: one logged chain | Gate attempts, triage, retries, flakes, review/fix cycles and merge decisions use the E-v self-improving harness events and queries (T-bp/T-bq), with cause links, pinned policy and measured costs. |
| G5: fair per-repo capacity | Each repo has its own merge queue and configurable full-CI lanes in `config.toml`. Local gates consume the shared weighted-unit budget; a busy repo cannot starve another eligible repo. |
| G6: scoped before review, full once at merge | A task runs lint, build and focused tests for the projects it touches, producing the existing scoped receipt before review. Run the full workflow-derived suite once on the stacked merge-group tip at merge time, shared by its members. Red diagnosis and invalidated tips are explicit, logged extra work. |
| G7: classified stacking | Stack up to five independent changes only when the local Ollama nimble classifier rates both non-interference and clear failure attribution confidently. Escalate uncertainty once to Haiku, then split if still uncertain. A group with overlapping files has at most two changes; conflicts never stack (W2). Log choices, confidence, outcomes and bisects for tuning. |

Observed motivations, supplied by the owner: gate 226's flaky Windows runner test needed manual triage; T-1h twice produced no output for 600 seconds on Windows; motif T-6m's gate 264 failed on changed ADR 0043 but returned only “blocked”; T-c needed four review cycles with one new finding each; already-reviewed land-candidates were reviewed again. These are acceptance scenarios, not retrospective machine-verified classifications.

### Grounding and integration boundaries

The implementation baseline inspected for this spec is `4157093`; the supplied read-only main snapshot has no E-v, T-bi or T-cd design artifacts. Their exact event identifiers and shared interfaces must be reconciled when integrating, rather than invented as already-landed facilities. Section 5 defines the semantic events, dimensions and queries this feature requires; E-v remains the authority for the common envelope, taxonomy, cost accounting and query registry. T-bi supplies the shared stuck/failure triage rung; T-cd supplies Windows Execution Containers. These are dependencies, not facilities this document claims exist today.

Current repo evidence:

- `drover/repos.py` reads per-repo registrations, validates `[run].platforms`, and resolves shared/platform-specific `full` and `scoped` gate argv. `unknown` prevents inventing a command.
- `drover/gate.py` and `drover/gatejob.py` bind receipts to exact SHAs and clean, unchanged trees, parse failures and support existing flaky-test retries. The latter's command loop alone does not establish workflow parity or a nonempty gate.
- `drover/dispatcher.py` sequences Windows then WSL, records gate/review runs, asks the currently shadow `gate_failure_class` question, and starts reviews after gates. `decide-criteria.json` currently combines environment and flakiness under `env_flaky`.
- `drover/landing.py` requires reviewed candidates, replays them on a fresh base, gates the batch tip and lands through the queue. `drover/contract.py` defines existing gate/outcome contracts; `task_events`, `decisions` and `run_stats` already hold history and usage.
- The existing scope fallback widens unmapped paths to a full run, landing formation accepts only disjoint paths, the landing lock is global, and gate leases are ranked slots. G5–G7 replace those behaviors as specified below; per-repo weighted lanes and classified overlapping groups are not claimed to exist in this baseline.
- This checkout has no `.github/workflows` directory. The supplied snapshot contains only fictional repo registrations, not the live motif, drover or PanGloss registrations. Migration must inventory those actual inputs; this spec does not assert their contents.

Only the Windows hub owns the ledger. WSL execution reports through existing hub boundaries. No second ledger, telemetry store, policy engine or agent scheduler is introduced.

## 1. Deriving a gate from workflows

### Inputs and required jobs

At the exact candidate SHA (the merge-group tip for the full gate), parse `.github/workflows/*.yml` and `*.yaml` as data. Use a bounded YAML parser with safe loading, duplicate-key rejection and no custom object constructors. YAML parsing is an implementation dependency decision; do not add a package implicitly. Preserve source file, job/step ID and line references in diagnostics. The normalized full graph defines parity; a task's scoped plan is a labeled subset and never reports full-suite coverage.

Build a normalized job graph for the repo's declared validation event context, normally a PR against its configured main branch, plus any validation jobs required only on push to main. Job names are hints, not an exclusion mechanism. Include build, compile, test, lint and repo validation jobs and their transitive `needs` dependencies, including reusable-workflow prerequisites. Publishing, release and deployment jobs are listed as excluded with a reason. Ambiguous jobs remain unresolved until a repo override classifies them. A job cannot disappear merely because its name lacks “test”.

Expand finite matrices including `include` and `exclude`, `runs-on` expressions and configuration/runtime variants. Preserve dependency ordering, workflow/job defaults, environment, shell, working directory and timeout semantics. Bound expansion to 64 variants by default; overflow is unsupported pending an explicit limit/configuration change. Duplicate test commands on Windows and Ubuntu remain separate obligations. Fail-fast may stop scheduling after red, but unexecuted variants remain incomplete.

Evaluate only a documented expression subset: literal booleans/comparisons, finite matrix values, registered event/ref/path facts, and explicit success/failure/always conditions. Step outputs, dynamic matrices, arbitrary functions and unresolved contexts are unsupported unless an explicit adapter handles them. A condition proved false is recorded with its inputs and reason; unknown is never treated as false. Event/path exclusions must be reported. A docs-only diff may skip jobs only when workflow semantics prove that skip; an empty selection is an explicit `not_applicable` result with evidence, never a passing zero-command gate. A solo repo with no applicable validation needs an explicit owner-approved no-check policy before mechanical landing.

### Placement and translation

| Workflow construct | Local treatment |
| --- | --- |
| `runs-on: windows-*` | Registered Windows placement and its capability inventory. |
| `runs-on: ubuntu-*` | Registered WSL Ubuntu distro and its capability inventory. |
| `macos-*`, unregistered self-hosted labels, `container:` | Unsupported placement; no substitution with Windows/WSL. |
| `run:` | Preserve script content and the workflow-selected shell, render only supported expressions, and hash both source and rendered script; invoke an approved shell by argv in an isolated checkout. No task-text interpolation. |
| Checkout action | Bounded adapter checks out the exact SHA. Nondefault depth, submodules, LFS and secondary repos require implemented equivalents or are unsupported. Never edit the owner's checkout. |
| Runtime/toolchain setup action | Adapter verifies the requested installed version and options, or reports missing capability. It does not silently use PATH's version or install anything. |
| Cache action | Optional acceleration only when its absence cannot alter correctness. Record hit/miss and keys; cold execution must still work. |
| Artifact upload/download | Upload may become a local hashed artifact receipt if only retention is needed. Cross-job downloads require a real local producer/consumer adapter; never skip a needed artifact. |
| Other marketplace actions, local/composite actions, reusable workflows | Unsupported by default. Explicit version-bound adapters may expand inspected behavior into local commands; recurse into local files only with bounded cycle/depth checks. Remote action code is never fetched and executed implicitly. |
| `services`, secrets, authenticated external calls | Unsupported by default; report names/requirements without values. An owner-configured service/credential adapter is needed, with explicit authority and availability. No service startup, secret copying, or install as a side effect of derivation. |

Honor GitHub's default shell behavior through explicit local shell adapters; merely running every command in the hub's shell is not parity. Each step gets its own process. Implement supported environment/output-file propagation and job outputs explicitly; otherwise flag them unsupported. Quote expression values as data according to the selected shell or reject the expression; do not concatenate untrusted refs, event text or paths into shell code.

This is a constrained workflow compiler. It emits a plan and diagnostics without an LLM. Unknown syntax fails closed. The plan is immutable and content-addressed, with candidate/base SHAs, workflow file digests, compiler/adapter versions, selected/excluded jobs and conditions, matrix values, placements, script/argv hashes, environment requirements, prerequisites, timeouts and artifact edges.

### Parity report and overrides

Report two coverage fractions and an environment assessment:

- Job coverage = fully supported required job variants / all required job variants.
- Obligation coverage = implemented required obligations / all required obligations. Obligations include placement, toolchain/setup, every behavior-bearing step, condition, service/secret and dependency/artifact edge. Count a blocked or unresolved obligation in the denominator. A mapped-but-unavailable capability is not implemented for this run.
- `parity_score = floor(100 * min(job_coverage, obligation_coverage))`. Zero required variants yields `not_applicable`, not 100. An unexpandable matrix/graph yields `unknown`, with unresolved counts, not a guessed percentage.
- Record requested OS labels and runtime versions beside actual Windows build, WSL distro release and toolchain versions. Host/distro placement implements G1; it does not assert byte-for-byte identity with a GitHub hosted image. Unmet pinned OS/runtime requirements block parity. Owner-accepted label differences are visible deviations, never proof of exact image identity.

A score of 100 means all required logical obligations have local equivalents and required capabilities; an unsupported required step prevents authoritative green. Explicit waivers do not inflate coverage. A solo repo needing a waiver remains a partial pre-check until the missing adapter is supplied or the owner approves a different, visibly non-parity gate policy. That exception is versioned and logged; it cannot be inferred from a successful legacy command.

Keep overrides in the hub-owned `~/.drover/repos/<repo>.toml`, resolved from the hub state directory, with platform-native paths only at execution. Extend the existing gate schema rather than replacing its command tables. The proposed configuration surface is:

```toml
[gate.workflow]
mode = "shadow" # shadow, authoritative, precheck; legacy command mode remains readable
include = [".github/workflows/*.yml", ".github/workflows/*.yaml"]
event = "pull_request"
required_jobs = ["ci.yml::build", "ci.yml::test"] # additive; dependencies are included

[gate.workflow.overrides."ci.yml::test"]
reason = "Use the already installed toolchain; same version and options"
source_sha256 = "<digest of the overridden job definition>"
adapter = "installed-toolchain-v1"
```

This example defines future fields, not a registration to copy into today's parser. Overrides can add required jobs, classify exclusions, select registered placements, bind adapters and declare local equivalents. Any command replacement must include its reason, exact source digest, owner/policy provenance and validation evidence. Additional local checks are labeled local-only. Repo-local workflow changes cannot self-approve an override or exclude checks by editing hub policy. Secrets are referenced by capability name, never stored in this TOML or a plan. Existing `[gate.commands]` can supply transitional equivalents but must be matched to source obligations before being called parity.

Derive and compare on every workflow addition, edit, deletion or rename, and on adapter, override or capability changes. Compare both main and candidate plans to detect deleted or weakened checks. Changes to workflow-discovered local action files, reusable workflows or gate scripts also invalidate the fingerprint. Emit a drift report with added/removed variants, altered commands/toolchains/placements and stale overrides. A changed source digest invalidates the corresponding override. Rederive against the landing tip; policy drift, unapproved weakening or unsupported new steps holds authoritative landing. A clean candidate cannot reuse a receipt generated under a different plan/policy/environment fingerprint.

## 2. Executing on Windows and WSL

The hub schedules plain local gate runs (`backend=local`, no model, no agent seat). Admission controls build capacity and disk/memory trackers; deriving multiple jobs never authorizes extra parallel builds. Within one admitted lane, initially execute topologically and sequentially, Windows then WSL where dependencies permit. Across repos, admitted lanes may progress concurrently within the shared budget. Missing WSL or a required Windows capability holds the affected gate with a precise systemic reason. Worker placement cannot downgrade the derived gate placements or bypass `[run].platforms`; configuration mismatches require correction.

### Per-repo queues, lanes and fair admission (G5)

Maintain one durable merge queue and main-update lock per registered repo, with configurable full-CI lanes in the hub's `~/.drover/config.toml`. A lane is permission to run one merge group's full suite, not an agent seat or one lane per member. The repo registration still owns commands, placements and scope maps. The following is a proposed schema extension, not configuration accepted by today's parser:

```toml
[capacity]
weighted_unit_budget = 6

[capacity.full_ci]
default_lanes = 1
default_units_per_lane = 1

[capacity.full_ci.repos.motif]
lanes = 1
units_per_lane = 2

[capacity.full_ci.repos.drover]
lanes = 1
units_per_lane = 1

[capacity.full_ci.repos.PanGloss]
lanes = 1
units_per_lane = 2
```

The numbers are illustrative owner-configured weights, not measured repo costs. Validate integer lanes ≥0 (zero explicitly pauses that repo), a positive integer `capacity.weighted_unit_budget` and positive integer unit costs. An omitted repo inherits the defaults. Reject an effective cost above the global weighted-unit budget with a configuration diagnostic, instead of leaving it waiting forever. Windows and WSL share this budget. Bind these lane costs to the common weighted admission ledger, not a new independent allowance. The current `parallel_cap` and gate slot lease are not themselves that weighted accounting; integration must make all heavy work visible to one admission authority before activation. Retain count/health caps as additional constraints, without allowing them to bypass fair reservation.

Admission atomically acquires a repo lane, weighted units and required placement/health permission; never hold one while waiting indefinitely for another. Full runs, pre-restore, scoped builds, flaky retries, baseline probes and bisects all consume units while executing. A retry/probe/bisect also consumes that repo's full-CI lane. Other heavy work declares its positive unit cost through common admission, conservatively defaulting to the repo's lane cost until measured costs are registered. Sequential jobs charge once for the active lane; any later job parallelism must reserve its additional units explicitly. Cheap triage uses model admission separately. A group queued for a repair releases compute capacity after its processes have stopped, while retaining its queue position and evidence. Lease expiry alone cannot free units for a possibly live process: reconcile owned PIDs/container state first.

Use fair round-robin selection across eligible repos, with priority and aging within each repo. Extra lanes may borrow idle capacity only while no other eligible repo is awaiting its turn; unused capacity is not permanently reserved. When the next repo's weighted request cannot yet fit, reserve the next released units for that turn rather than repeatedly admitting cheaper work from another repo. Include worker/scoped-build admission in that reservation so non-gate work cannot consume it first. Skip paused/unhealthy repos with an explicit reason, without blocking healthy ones. With finite run deadlines and eventual healthy capacity, every continuously eligible repo gets a turn after a bounded number of other repo admissions, independent of another repo's priority or backlog. Log queue age, admission turns, units and blocked reasons to verify this property.

More than one lane per repo permits speculative groups on the same recorded base, but only one main update under its repo lock. If an earlier group advances main, a later lane's old tip cannot land: replay and invalidate its old receipt, then enqueue the new tip for a fresh full run. Default one lane minimizes this G6 cost. Never combine repos into one group, serialize all repos under the old global landing lock, or evade lane/unit limits for diagnostics. Capacity/policy changes are versioned; reducing a limit drains active work without silently killing or duplicating it.

Prepare a clean, task-owned checkout for each job that needs isolated workspace state. Jobs share only explicitly declared artifacts. Do not depend on another job's ignored build outputs or warm workspace. Keep generated scripts, receipts and logs outside tracked source. Gates verify exact HEAD and a clean tree before and after execution; tracked generation requires a designated verification step and must leave the tree clean. An empty command list, missing receipt, timeout, lost process, dirty tree or unexecuted required variant is never green.

### Restore and sandbox boundary

Split preparation from build/test without dropping restore obligations:

1. Pin candidate, plan, lockfiles, toolchains and placement. Check available disk before heavy work and acquire the common weighted admission lease plus the applicable repo lane. Migrate the existing gate lease through that admission boundary rather than acquiring an independent extra allowance.
2. Pre-restore/download approved dependencies outside any sandbox, under a bounded preparation command and scoped credential/network authority. Record commands, exit status, dependency/lock hashes, cache manifest and logs. Do not run arbitrary candidate-controlled build hooks with hub credentials: restore adapters must suppress hooks/evaluation or perform acquisition in an unprivileged preparation context without owner credentials. A restore that cannot be separated safely is unsupported until an adapter exists.
3. Use per-platform caches keyed by toolchain and dependency inputs. Recreate required local assets in the isolated job workspace; Windows/WSL paths and native outputs are not interchangeable. A changed lockfile or SDK invalidates preparation. Missing packages are preparation failures, not worker blame.
4. Execute build/test using restored inputs with the ecosystem's no-restore/offline equivalent where supported. Record that the workflow's restore obligation was fulfilled in preparation. Network-dependent tests require an explicit capability; sandbox denial is not silently solved by disabling isolation.

Windows initially uses the existing plain local runner with an explicit `isolation=host` receipt. Once T-cd is integrated, gate execution runs inside its Execution Container with the prepared source/dependencies and declared capabilities; record the container/profile identity. Preparation remains outside that boundary. Before/after T-cd evidence has different environment fingerprints and is not interchangeable. A repo requiring container isolation waits if T-cd is unavailable, rather than silently falling back. WSL jobs execute in the registered Ubuntu distro through the existing WSL runner boundary. Docker is deferred.

Stream stdout/stderr to durable per-step logs with job/step boundaries, timestamps and exit status, while emitting a runner heartbeat at least every 30 seconds independently of command output. Preserve separate launch, preparation, command-output and heartbeat times. Honor workflow timeouts, capped by registered repo limits; absent a workflow limit, retain the repo's gate timeout. Retain its idle-output limit too, but treat output silence as a triage signal distinct from a dead runner. The T-bi rung receives a 600-second no-output signal by default; this does not extend a shorter existing timeout or kill an active command merely for silence. Rung polling cannot extend the absolute deadline. Timeout cleanup addresses only recorded gate PIDs and their owned process tree/container; never another repo's process.

### The 600-second no-output case

The reported T-ce failure, `[windows gate failed] gate timed out (no output for 600s)`, establishes a runner timeout, not its root cause. The present `drover/runner.py` enforces idle silence as a terminating timeout; adopting the triage signal above therefore requires an explicit gate-runner change. Existing worker idle-timeout behavior stays under its own policy. Until that adapter lands, retain the actual timeout result and send its bounded status facts to triage; documentation changes or a WSL pass cannot clear the Windows failure.

For the new gate adapter, use independent monotonic clocks for launch acknowledgement, last child stdout/stderr byte, runner heartbeat and absolute deadline. A log header, hub poll, lease renewal or heartbeat does not reset the child-output clock. Send heartbeats through runner status, not fabricated child output; liveness is not progress or proof of success. No-output duration starts when the child starts, even if it never writes a byte.

| Signal at the silence threshold | Required handling |
| --- | --- |
| Child is live and runner heartbeat is fresh | Emit one stuck-triage request per silent step/episode and continue only within the existing absolute deadline. Record any wait recommendation. Do not terminate solely for idle output, repeat triage on every poll, or consume the flaky-rerun allowance. |
| Runner heartbeat is stale, child status is unknown, or launch was never acknowledged | Reconcile the recorded run and owned PID/container before deciding whether it is lost. Emit an explicit health/launch diagnosis with available timings; do not infer a flaky test or launch another copy. |
| Absolute deadline expires, including during triage | Record timeout and cleanup outcome, retain any partial log and preparation receipt, and cancel only the owned process tree/container. Late triage cannot revive the attempt or replace its result. An unfinished cleanup remains a reconciliation hold. |
| Child exits | Record its real exit status and final tree/step checks, including when it produced no output. Exit zero can pass a required command; a missing receipt or unexecuted command cannot. |

The bounded triage evidence for a zero-output run is its job/step, redacted command identity, placement, start/last-output/heartbeat/deadline facts, owned PID state and timeout/cleanup status. Test and file:line are explicitly unavailable. Both T-1h hangs must remain distinct attempts linked to the same systemic diagnosis when supported by evidence. Do not synthesize an error location or ask the docs worker to modify code to compensate for missing runner facts.

Each job receipt includes run/attempt IDs, exact SHA/base, plan/policy/workflow/override/environment fingerprints, placement, preparation receipt, executed step statuses, artifact/log digests, timing, tree checks and any retry link. Include receipt stage, repo lane/weighted lease, merge-group ID/revision and ordered member SHAs for merge runs; scoped receipts carry their impact-map and selected-check proof. Aggregate green requires every required variant to pass or have an evidenced workflow-semantic skip, plus the applicable parity policy. Diagnostic filtered tests and baseline probes are separate receipts; neither can substitute for the required gate. Previously passed jobs may be reused only at the same SHA and fingerprints with intact required artifacts; a retry executes the entire failed job and its invalidated dependencies, not only a failing test class.

## 3. Scoped checks, review eligibility and mechanical landing

### Two stages, one normal full run (G6)

The normal solo-repo path is **worker change → scoped checks → review or exemption → repo merge queue → classified stack → full suite on its tip → mechanical fast-forward**. A landing batch is the existing domain term; “merge group” here means that same batch with a frozen ordered membership/base/tip. A singleton is a valid merge group.

Before review, run only the task's lint, build and focused tests for its touched projects and declared affected dependents, using the existing scope-map/command machinery and scoped receipt. Include applicable documentation validators for docs tasks. Record the selected projects/checks and path-to-project evidence at the exact task SHA, along with required placements, plan/environment and clean-tree checks. A fix repeats these affected checks before focused re-review; it does not trigger a per-task full suite. Mixed changes take the union of their mapped checks. An unmapped path or absent focused command is `scope_unresolved`: repair/configure the mapping or record an owner-approved, evidenced no-applicable-check policy. Do not silently fall back to a full pre-review run as the legacy selector does. A workflow/shared-build change may affect every project, but this must be an explicit impact mapping; it cannot masquerade as a narrow receipt.

Use a versioned receipt stage, `scoped_review`, versus `merge_full` (and `diagnostic` for probes). This extends the existing scoped receipt rather than creating a separate proof store. Scoped green licenses review/queue eligibility only. It cannot satisfy full parity, clear a red group or authorize landing. Existing scoped-chain validation may consume a previously known full parent when applicable; G6 never requires generating a new full parent per task. New stage-aware consumers must handle task revisions with multiple commits; legacy parent-plus-one-commit landing proofs are not silently broadened. Old full task receipts remain history and do not create a requirement to repeat them before review.

After required reviews/exemptions are valid, replay the frozen members on recorded main, derive the full workflow graph at the resulting tip, and run it once across all required placements/matrix variants. One aggregate full receipt covers that tip and all group members; it is not one full run per member, nor one before review plus another at merge. Resume/reconcile an existing same-tip run or reuse its valid receipt instead of launching it again during queue polling, finish processing, or review reuse. A normal green tip lands immediately after the safety checks below without another review/full run.

“Once” describes this normal path, not permission to land an untested tip or suppress red evidence. Extra execution requires a recorded reason: one flaky failed-job retry, bounded baseline/bisect diagnostics, changed code, changed membership/base, or invalidated plan/policy/environment/artifacts. A new tested tip is a new group revision linked to its predecessor. Reusing unaffected same-tip job receipts is allowed under section 2; a changed tip always requires a complete full aggregate for that tip. Review fixes after a group red return only the affected task to scoped checks and required re-review before a revised group is gated.

### Selecting a stack (G7 and W2)

Formation is per repo, within configured lanes, from queue-eligible candidates. Start with the oldest eligible candidate at its aged priority, then consider companions without waiting indefinitely for a group to fill. Freeze membership, order, task revisions, base and policy before launching full CI. Up to five changes may stack when all are independent and attributable. Changed-file disjointness is a useful filter, not proof: APIs, dependencies, shared build inputs, generated files and behavior may couple disjoint paths.

Enforce W2 deterministically before accepting model advice: a group with any same-file overlap has **at most two members total**, including any otherwise disjoint companions; a conflict never stacks. Perform a dry replay in an owned scratch checkout to detect conflicts. Reject the conflicting combination without resolving it in the queue; return the affected candidate for an ordinary worker fix/rebase and renewed scoped/review evidence. Non-overlapping hunks in one file may qualify as the dirty pair only with the same independence/attribution evidence as clean groups. Overlap is not a review exemption: if replay changes a reviewed path's preimage, the review-reuse rule below requires renewed affected coverage before full CI; otherwise split the pair. Missing provenance, dependencies between members, outstanding holds, different repos, or unapproved gate weakening cannot be accepted by any model.

Ask the local Ollama **nimble** classifier a versioned stacking question, separate from failure-class triage. Supply bounded task summaries, changed paths/hunk fingerprints, project/dependency/ownership maps, relevant public-interface/build changes, focused-check evidence and proposed order/base. The output must rate both predicates for the whole group: (1) members do not affect each other, (2) a likely test/build failure is clearly assignable to one member. It must cite supplied evidence and risks for each pair and identify an ownership basis for the affected checks; path membership alone is insufficient. No full logs, agent code review, edits or gate execution occur in this call.

Persist a schema-validated result containing `group_id`, `revision`, ordered member SHAs, `base_sha`, `evidence_refs`, `non_interference` and `failure_assignability` (each `yes|no|unknown` plus confidence in [0,1]), bounded pair/ownership reasons, and `recommendation=stack|split`. Joint confidence is the smaller predicate confidence; initial threshold is 0.8 under pinned policy. Both predicates must be `yes` at or above threshold and all mechanical checks must pass. A confident `no` splits the group. An unknown, low-confidence, invalid or timed-out nimble result escalates once to Haiku with the same evidence and a bounded supplementary excerpt if useful. If Haiku is unavailable, still uncertain, or contradicts unresolved evidence, split deterministically into smaller valid groups, ultimately singletons. Do not keep shopping models for approval. A singleton needs no compatibility call but records its formation reason.

Bound nimble to 2,048 input/512 output tokens and a 5-second model deadline; Haiku to 3,072 input/512 output and 60 seconds. Maximum 6,144 tokens across the two calls for one proposed group revision; incomplete evidence stays unknown rather than truncating away risk. These are model-admitted decisions, not agent gate runners. Changed inputs invalidate a verdict; cache by membership/order/base/evidence/policy fingerprints to avoid repeated calls for the same proposal. Log accepted, rejected, split and escalated proposals, model/version, both scores, criteria/threshold, costs, mechanical overlap/conflict checks and final rule action. Later red attribution/bisect and green/merge outcomes feed back to these decision IDs for the E-v tuner; green alone does not prove either predicate.

### Review and merge rules (G2)

Determine eligibility from task kind **and the actual diff**, provenance and pinned repo policy. A worker's “mechanical” label is not authority. Record the result as review-required, review-exempt or review-reused; do not fabricate a Sol run or `LAND@sha` for an exemption.

| Candidate | Low risk | High risk / safety boundary |
| --- | --- | --- |
| Docs-only | Skip agent review after confirming only allowed documentation paths/content changed; scoped checks first and full applicable gate on the merge group remain required. | Same exemption for genuine documentation. Existing explicit owner holds and approval requirements remain. Executable snippets consumed by tooling, workflow/config changes and generated runtime inputs do not qualify just because they live under `docs/`. |
| Mechanical | Skip agent review for a declared, deterministic transform with mechanically verified before/after invariants and scope. | Skip only when the same invariants actually prove the transform and required owner authorization is already recorded. Semantic/ambiguous transforms are code changes and need Sol. |
| Already-reviewed land-candidate | Reuse valid review coverage; no new review because the task is now landing. | Reuse only if the review met the applicable risk policy and no new risk/owner hold invalidates it. |
| New agent-written code, including fixes | One Sol review of the complete candidate diff after scoped green. | Sol remains required, plus any existing owner/high-risk checks. Do not substitute Luna/Haiku triage for code review. |
| Unknown kind/provenance or invalid evidence | Require Sol or obtain missing evidence. | Hold when required authorization/evidence is missing. |

Docs-only eligibility uses a repo-owned allowlist plus content/consumer checks, excludes symlink/mode changes and mixed code changes, and never means “skip CI.” A mechanical transform supplies a registered verifier; a model's assertion of equivalence is insufficient. Unsafe classification defaults to review-required. Risk changes cannot be made solely to obtain an exemption. No exemption bypasses scope, task acceptance, dependency ordering, explicit owner holds, destructive-operation authorization, required platform gates or the team-repo policy below.

Review receipts pin task revision, full reviewed SHA, base, canonical changed-file fingerprints, reviewer/model, policy/risk, findings and verdict. On ordinary exact-SHA reuse, validate these against the current candidate and outstanding holds. For a conflict-free landing replay onto a newer base, reuse coverage only with mechanical proof that every changed path's before/after blob IDs and modes are identical to the reviewed change, with no added/removed paths or edited conflict resolutions. Record the original review and replay proof; never relabel the old review as having read the new SHA. Changes elsewhere on main still require a full gate on the new landing tip. Changed preimages, conflict resolution, changed requirements/risk, code edits or unverifiable review provenance require a fresh Sol review of the affected candidate. A historical review by a different reviewer needs an explicit policy compatibility rule; “reviewed before” alone is insufficient.

The first Sol review should report all material findings it can establish in one pass, with stable finding IDs. HOLD → worker fix → scoped green → focused Sol re-review links those IDs and checks the fix plus new regressions introduced by it. Re-review may report newly established material issues, but records why they were not found earlier. Persist every round, including incomplete review attempts. After two HOLD/fix rounds, route to the shared stuck triage for a summary and escalation decision instead of an unbounded automatic loop. It cannot turn HOLD into LAND. An accepted LAND is reused through queue entry; there is no extra review of every land-candidate.

For solo repos, the landing queue mechanically lands an eligible full-green merge group by fast-forward only. Under its per-repo lock, validate scope, holds, required review/exemption, stacking decision, exact tested tip, clean tree and fresh plan/policy/environment evidence, then compare main to the expected base immediately before updating. If main moves, rebuild/re-gate the tip; reuse review only by the proof above. Never reuse a task receipt as a batch-tip receipt. Record the merge decision, attempted effect and verified resulting SHA, including a crash/reconciliation outcome. Push/publish permission is unchanged; green does not authorize those effects. Workers still never merge themselves.

### Red groups, diagnosis and red-rate consequences

Scoped checks cannot catch every interaction. Moving the full suite to merge time can increase the original merge-group red rate, delayed worker feedback, queue latency and diagnostic cost even while reducing total full runs. Measure those costs rather than treating focused green as proof of integration. No member is charged or removed merely because its group is red, nor because the pre-stack classifier predicted an owner.

First send only the failing slice through G3. Flaky, environment/sandbox and comparable-main failures follow section 4 before any bisect or worker blame. For a confirmed change-caused failure, deterministic test/project ownership plus evidence may identify one member; return its compact brief only to that worker. Without a defensible single owner, do bounded bisection on subsets of the frozen group at the same recorded base. Preserve dependency order, record each subset's actual replayed SHA and complete check inputs, and reuse same-input diagnostics. Prefer the failing check/job as a diagnostic; a narrowed pass is never a landing receipt.

Do not assume monotonic prefix failure means one culprit: two changes may fail only together. For groups of at most five, allow at most six new diagnostic subset executions per original red episode, each with normal timeouts/admission. A matching red singleton with a comparable green base supports attribution; two green halves and a red combination indicate an interaction to investigate, not blame on whichever member was added last. A different signature starts a separately linked failure, not confirmation of the original. If attribution remains ambiguous, preserve members/reviews, record the interaction or unknown outcome, split for sequential singleton landing attempts, or hold for diagnosis if a safe split cannot be proved. Exhausted diagnostics never auto-drop a task. Every split subset that will land needs its own complete merge-full receipt, including after a culprit is removed; a passing prefix or scoped receipt cannot cover the remainder.

Count the once-per-tip initial full gate separately from flaky retries, baseline probes, bisect subsets and regenerated tips. Define original red rate as red first full attempts / completed first full attempts for group revisions, split by repo/policy/group size/dirty status; exclude scoped checks and diagnostic attempts from that denominator, and report unknown/lost attempts separately. Also report unique-change throughput, queue wait, full runs per landed change, extra-run reasons, attribution accuracy/unknown rate, bisect count/wall time and classifier/triage/rework tokens. The same change participating in several revised groups is counted once for throughput, but every expensive attempt remains visible. Do not equate the old all-gate `red_rate` with this metric during migration.

The tuner can propose reducing group size or stricter confidence/ownership requirements when red or bisect cost rises, with pinned/versioned decisions. It may never exceed five, relax W2, erase red attempts or insert routine full-suite pre-review runs. Do not automatically disable grouping solely because the old global ten-minute median heuristic says so; tune per repo from measured throughput and diagnosis cost under G5 fairness. These consequences, stacking outcomes and their confidence calibration belong in G4 events even when a group never merges.

## 4. Shared cheap triage rung

Gate red and stuck/no-output signals enter the same T-bi bounded triage service with different `trigger` values. The service is a short classification call to an admitted Luna or Haiku seat, not a repository-editing worker and not part of gate execution. It cannot run commands, browse the full log, mutate files, grant permissions or merge. The hub mechanically extracts and redacts only failing sections first; success output, complete transcripts and full repo diffs are excluded.

Record raw gate failure immediately, but defer worker retry, attempt penalties and attribution-based quality metrics until triage validates the cause. The current `_failed` path must not run first and charge the worker before this rung. Preserve raw gate reliability statistics independently of worker blame.

Input includes task/run/step IDs, trigger, exit/timeout/heartbeat facts, failing test/error/file:line records, changed-path membership, failure signature, rerun count, placement/environment and any already-known baseline evidence. Group failures also supply frozen group/revision/member IDs and bounded ownership evidence; do not copy the excerpt into separate model calls for each member. Bound initial input, including instructions/schema, to 2,048 tokens and output to 512 tokens, with a 60-second call deadline. At most one supplementary failing excerpt is allowed (1,024 input, 256 output); the total episode ceiling is 3,840 tokens and 120 seconds of model-call time. T-bi and gate triage share that ceiling for the same failure episode. A retry of an ambiguous model request counts against it; no hidden chain of reasoning calls. Persist configured caps, measured tokens, model/seat and timeout. No eligible cheap seat, malformed output, low confidence or exhausted budget yields `unknown` and a bounded escalation record, not a stronger full-log review by default.

The semantic output schema is versioned; E-v supplies its envelope and T-bi owns the shared transport. Every key below is required, nullable fields remain explicit, and unknown keys/oversize values are rejected. This example describes a hypothetical ADR validator failure:

```json
{
  "schema_version": 3,
  "trigger": "gate_failure",
  "gate_run_id": 9001,
  "group_id": null,
  "group_revision": null,
  "attributed_task_id": "T-6m",
  "failure_id": "step-3:adr-0043",
  "classification": "change_caused",
  "confidence": 0.93,
  "failure_kind": "test_logic",
  "test": "ADR validation",
  "error": "Changed ADR violates the repository validator",
  "file": "docs/adr/0043.md",
  "line": null,
  "evidence_refs": ["gate:9001/step:3/log:lines:120-134"],
  "baseline_receipt_id": null,
  "systemic_task_id": null,
  "suggested_action": "worker_fix",
  "summary_lines": ["ADR validation: changed ADR violates repository validator; docs/adr/0043.md (line unavailable)."]
}
```

Enums: `trigger` = `gate_failure|gate_stuck`; `classification` = `flaky|environment_sandbox|baseline|change_caused|unknown`; `suggested_action` = `rerun_once|link_systemic_fix|check_baseline|worker_fix|bisect_group|escalate`. `failure_kind` retains the legacy detail enum `syntax|type|test_logic|build_system|env_flaky|scope_violation`, or null; it does not control attribution. Group ID/revision are both null for a standalone scoped failure and both present for a group failure. `attributed_task_id` is a validated member or null; a change-caused group failure with uncertain ownership uses null and `bisect_group`, never a guessed worker. Confidence is in [0,1], summary has at most ten lines and 1,500 characters total, error at most 300 characters, and evidence references must belong to this episode. File paths are repo-relative or null, line is a positive integer or null; never invent a location. Store separate results for independent failures under one gate episode. All must be resolved before green; flaky routing for one cannot hide another deterministic failure.

Promote `gate_failure_class` from shadow to live using a new criteria version for the routing enum above, retaining detail classes separately. Old answers remain under their original criteria version; `env_flaky` history cannot be retroactively split without evidence. A live verdict requires confidence ≥0.8 and a valid evidence-backed action. Otherwise classify unknown and escalate with the bounded excerpt. Keep the existing decision ID, rule answer and eventual outcome links. The model proposes; hub rules validate baseline and rerun eligibility, deduplicate work and execute the action.

| Verdict | Deterministic action and task treatment |
| --- | --- |
| Flaky | Rerun once, mechanically, at the identical SHA, plan and environment. One automatic flaky rerun per gate episode, shared with legacy retry facilities; disable nested per-test retries. Rerun the failed job and invalidated dependencies. A pass records an observed flake and `passed_with_flakes`; only then can the aggregate gate become green. Another failure exhausts the allowance and needs diagnosis, not another automatic retry. |
| Environment or sandbox | Attach to an existing systemic fix or file one, deduplicated by repo/capability/failure signature. Record disk, missing toolchain, restore, container denial or runner-health evidence. Preserve the candidate; do not debit worker attempts or reduce worker quality scores. Wait for the prerequisite and then run a fresh gate; never escape the sandbox automatically. |
| Already failing on main | Require a comparable existing baseline receipt or run one bounded diagnostic on the exact recorded main SHA in an isolated checkout, with the same failing check, inputs and environment. Preserve candidate evidence while waiting. Baseline failure is not permission to merge red. |
| Caused by this change | Return at most ten lines and 1,500 characters total, including test/check, error, file:line (or explicitly unavailable), evidence links and failure ID. Resume the responsible worker through the existing retry policy. Do not send the full log or only “blocked.” Changed-file membership is evidence, not proof of causation by itself. |
| Unknown / conflicting evidence | Keep the task pending diagnosis with a specific reason and excerpt reference. Escalate through T-bi's bounded escalation path; missing output alone is neither flaky nor a code defect. No blind worker rerun. |

Budget one baseline probe per failure signature, main SHA, plan and environment; reuse comparable results and schedule through normal gate admission. A probe has the same command/time/resource bounds as its gate job and is labeled diagnostic, never candidate success. A suggested baseline verdict without proof first executes `check_baseline`; its result appends confirmed/rejected attribution. Known baseline code may fail under a different candidate workflow: record incomparable evidence and escalate instead of blaming or clearing the task.

T-bi handles a live-but-silent process using heartbeat/PID facts and the remaining absolute timeout. It may advise waiting within that deadline; only the deterministic runner cancels an owned process at timeout or an authorized stop. A runner still active after a launch timeout is reconciled by its run ID before any new launch. Repeated T-1h-style hangs attach to one systemic issue with both attempts and timings. UI state must distinguish waiting on systemic repair, waiting on baseline repair, worker fix, and triage unknown; no generic blocked label that loses the reason.

Decision correctness uses later evidence, not “next run passed” alone: flaky requires a same-input red→green pair; baseline requires the comparable baseline signature; environment requires repair/recheck evidence; change-caused requires linked fix/recheck evidence. A next run with different code or environment cannot by itself validate the original attribution. Append corrections and keep unconfirmed outcomes unknown.
