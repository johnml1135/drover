# Safe self-reload for Drover

Date: 2026-10-17. Status: proposed; recommendations used without an interactive owner.
Deliverable: research and specification only. Implementation is a separate backlog.

## Problem and intent

After Drover lands its own changes, the owner wants the running hub to use them without a lead killing and restarting it. Reload must preserve detached workers and reviews, exclude active landing and gates, and recover automatically if the replacement cannot start. The owner also needs one supported start command. The manual-restart pain is the task's supplied requirement, not an observation of a live process.

All **current-behavior** references below are relative to `drover@main`, fixed at Git object `6df8e93261c7d79f216f025c529b9eec9c076a52` available in the supplied read-only checkout; its checked-out HEAD may advance. `T-7:` references use the read-only T-7 checkout, fixed at `69130500284e803866fc293e03ab612c09353d2b`. Everything described as proposed or required is new behavior. Implementers must reconcile intervening changes before editing. Schema numbers in worked examples are synthetic matching release/ledger contracts, never an assumption about the owner's ledger. The externally assigned research worktree is older than this main baseline; no product files are changed here.

## Goals, boundaries and alternatives

Required: automatic reload after relevant successful self-landings, safe manual “Reload now”, persistent auto on/off, preserved owner dispatch preference, adoption without duplicate launches, rollback to a known healthy runtime, durable events, and a non-elevated Windows start command. No new packages or services.

Non-goals: zero HTTP downtime, arbitrary schema/dependency upgrades, automatic Git revert/reset, supervisor hot replacement, runtime garbage collection, changes to admission capacity or landing/push policy. Safety covers **hub-managed** gates and landings. Standalone `drover.landing` also exists (`drover/landing.py:561-595`); owners must turn auto-reload off before independent CLI gates/landings and finish them before “Reload now”. Concurrent unregistered owner commands are outside this protocol.

| Option | Evaluation |
| --- | --- |
| **Stable small parent loop, scheduled task as optional launcher (recommended)** | Keeps recovery logic alive if child imports fail; owns old/new identities and runtime selection. Requires a durable protocol and immutable runtime copies. Reuses the installed per-user task rather than adding a service. |
| In-process re-exec/restart | Smaller entrypoint change but no independent observer remains to verify startup or select the old runtime; must still solve custom listener/thread drain. Reject for v1. |
| Uvicorn reload / file watcher | Ties restart to filesystem changes rather than completed gated landing; the custom two-listener lifecycle is outside Uvicorn's lifespan (`hub/app.py:25-26`). Reject as the safety authority. |

## Proposed architecture

`Start-DroverHub.ps1` → installed stdlib supervisor → exactly one hub child → detached runners. The scheduled task invokes its installed frozen copy of the same wrapper. Parent and child share an owner-only state directory and protocol version 1. The supervisor never opens the ledger or imports mutable hub application code.

The installer copies `hub/supervisor.py`, `hub/runtime.py`, `hub/reload_protocol.py`, and `hub/reload_machine.py` to `<state>/hub-runtime/bootstrap/v1/`. They must run as standalone stdlib modules with no imports from `drover` or application dependencies. Copy is an explicit owner installation action, never an automatic reload action. Parent holds `supervisor.lock`; child holds the existing `dispatcher.lock`. Neither lock substitutes for the other. A second start reports the existing supervisor status; it never spawns another child. Bootstrap changes require a stopped, owner-managed upgrade. Also freeze a copy of `Start-DroverHub.ps1` there for scheduled-task invocation; enrollment compatibility covers that wrapper and both installer scripts as well as the four Python peers. Source wrapper launches the installed parent using the enrollment paths; installed wrapper resolves source from enrollment, not its own parent directory.

At enrollment, export a clean source HEAD with `git archive --format=zip <40-hex-sha>` to a temporary directory; validate entries, then atomically rename to `<state>/hub-runtime/releases/<sha>/`. Archive all tracked files, no `.git`, untracked files, traversal, links, or private state. Store a content manifest. On first enrollment, run the read-only baseline probe from the temporary immutable export before publishing enrollment/bootstrap or the final baseline manifest; only after compatibility succeeds may the installer finalize the release and retarget the scheduled task. Never rewrite an existing release. Keep all v1 releases: detached runners can still import their launch generation. No worktree is created or pruned.

Run the existing installed `hub/.venv/Scripts/python.exe` directly with `-m hub`, CWD and sole project import root set to the release. Strip inherited project `PYTHONPATH` entries before setting it. Do not run `uv sync`, resolve dependencies, or install on reload. The existing installation creates the venv (`hub/scripts/Install-Drover.ps1:88-97`); dependencies are declared in `hub/pyproject.toml:5-16`.

Pin absolute ledger, runs, repo-config, config-home, token, source-root and overlay paths in the enrollment manifest. Set `DROVER_OVERLAY` to the original source overlay and preserve the owner environment. This matters because `drover/config.py:25,465-472` otherwise derives the overlay from the imported checkout and `drover/launch.py:402,440-449` derives runner code from its own package. Repo configs continue pointing to actual repositories; snapshots are never a landing destination. Both Windows and WSL runner imports come from the retained release. Require the release path to be reachable through the existing WSL drive mapping before enabling reload with WSL runs.

## Detection and eligibility

1. Enroll one explicit source checkout/default branch and its canonical Git common-directory identity. Runtime/source identity comes from the enrollment manifest, not the task's repo name or snapshot `__file__`.
2. After `LandingService._land_repo` returns `outcome=landed` and its `finally` finishes, inspect `batch_id`, `tip`, enrolled source HEAD and repo identity. Use the persisted batch as evidence. Require source HEAD exactly equals that tip and tip is a descendant of the running SHA. Different repositories, failed/stale/remote-only landings do not request reload.
3. Compare `git diff --name-only --no-renames <running_sha> <tip> -- hub/ drover/`. Include additions, deletions and rename source/destination by disabling rename detection. Any such change is relevant; docs-only changes are not. A relevant landing requests even when auto is off, so the UI shows pending work. Bootstrap-only edits request an owner upgrade instead of restart.
4. Reconcile successful recorded batches at startup and every 30 seconds to cover a crash between landing and notification (`drover/landing.py:541-550` is the existing batch receipt). Never execute an unrecorded source HEAD automatically. Coalesce eligible tips to the newest descendant **before** drain; pin one SHA once draining starts. A later tip waits for the next cycle.
5. Require clean source checkout, exact 40-hex SHA, valid immutable release, protocol/run-format version 1, identical `hub/uv.lock` and `hub/pyproject.toml`, identical `drover/ledger/schema.py` content, unchanged configured interpreter identity, and actual ledger schema version equal to the enrolled version. V1 deliberately treats any schema-file change conservatively, even comments. Stage failures leave the old child running with a pending reason.
6. Disallow automatic candidates that change any bootstrap source file. Do not dynamically load candidate code to inspect compatibility: inspect Git blobs/manifests with the stable parent. Protocol/run-format changes must bump constants and require owner enrollment. Unknown compatibility fails closed.

“Reload now” may restart the current enrolled SHA or use the newest eligible recorded tip; it cannot accept an arbitrary ref/path/command. Auto defaults **off** on enrollment. A repeated request uses the same durable idempotency key and is coalesced. Turning auto off cancels an automatic request before drain, but does not interrupt a drain already underway. The owner cannot force through blockers.

Candidate checks and recovery checks are separate contracts. `check_eligibility` applies the source identity, clean checkout, exact HEAD/target and ancestry rules above before staging/drain and again immediately before **candidate** spawn. If HEAD advances after target pinning, leave the old child running; if it already exited, recover its retained runtime. Do not silently substitute a later tip.

`check_recovery` selects only a retained release named by the durable last-healthy `active`/`previous` receipt (or the explicit installer-enrolled baseline for first startup). Recheck the receipt's manifest digest, every retained file digest, release SHA, enrollment paths, protocol/run format, dependency/schema/bootstrap digests against enrollment, configured interpreter identity and required WSL reachability. Never re-export or inspect current source HEAD, cleanliness, ancestry or current source blobs for recovery. Thus source may remain at B, advance to C or be dirty while healthy retained A recovers. A corrupt release, changed interpreter or incompatible retained contract blocks recovery. This path cannot authorize a new candidate or arbitrary SHA.

The parent never opens SQLite. While a child is alive, candidate eligibility requires fresh live `ledger_schema` evidence as defined below and passes that integer to `check_eligibility`. Once no child is alive, retained recovery may spawn **only with admission closed**, based on the enrollment/healthy manifest; historical schema evidence is not fresh readiness. Every supervised child, including first start, crash recovery and fallback, performs the following checks **before constructing Store or adopting/writing runs**. Its fresh schema report must pass the same readiness checks before any commit/resume. No age exception permits old evidence to claim ready.

**Release and ledger compatibility:** The release's required schema is `max((version for version, _ in drover.ledger.schema.MIGRATIONS), default=0)`, evaluated by that immutable release's interpreter, independently of the observed ledger. Enrollment invokes that release's probe-only `-m hub --schema-preflight --ledger <pinned-path>` under the native dispatcher lock. It succeeds only if actual schema equals required schema; only then record `enrollment.ledger_schema` and `enrollment.required_schema`, both equal to the probe's separate `ledger_schema`/`required_schema` results. A version-3 ledger against required version 4 must refuse enrollment without migration, bootstrap/enrollment publication or scheduled-task registration. Missing, empty, malformed, unreadable, older or newer ledgers also refuse. The owner must complete any legacy setup/migration separately before enrollment. Each release manifest records `required_schema` and `ledger_schema`; both must equal enrollment's verified pair. Candidate schema-blob equality permits copying that anchored requirement; every child independently recomputes it before checking the ledger. Never bless an arbitrary observed version as the expected contract.

**Read-only preflight:** Add `hub.__main__.probe_ledger(db_path: Path, *, expected_schema: int | None = None) -> dict[str, int]`. It derives the release requirement above; when expected_schema is supplied it must equal that requirement. Open `db_path.resolve().as_uri() + '?mode=ro'` using `sqlite3.connect(..., uri=True, isolation_level=None, timeout=10)`, call `schema_version`, require actual equals required, return the separate values, and always close. Do not call ledger `connect`, create directories, create a missing database, migrate, issue DDL/DML or set journal_mode. Respect committed WAL contents; do not use `immutable=1` or silently fall back to a writable open. If SQLite cannot read safely, refuse. Failed preflight leaves database contents, schema and journal mode unchanged and creates no missing database or parent. Supervised startup holds the native dispatcher lock, checks `enrollment.ledger_schema == enrollment.required_schema == manifest.ledger_schema == manifest.required_schema == code_required_schema`, then probes with that expectation. The lock remains held through Store startup and adoption; installation's probe-only command releases it and exits without constructing the app.

**Store lifetime:** Extend `Store(db_path, publish=None, *, migrate_db: bool=True, expected_schema: int | None=None)`. Supervised app construction always supplies `migrate_db=False` and the verified requirement; reject missing/invalid expected schema in this mode. Every thread-local connection, including later/reopened ones, uses `connect(self.path, migrate_db=False)` and checks actual schema against the expected requirement before exposing the connection; close/refuse on mismatch or read failure. Never retry with migration enabled. Existing unsupervised callers retain today's migrating default. Readiness is a further check, not permission to migrate after a successful preflight. This deliberately separates the read-only probe from the normal writable, migration-disabled operational connections.

## Drain, handoff and readiness

The proposed `ActivityBarrier` is shared across hub dispatcher, landing, services and API admission. Its mutex atomically changes admission to closed and accounts for synchronous entry sections. Every claim, worker/review/gate launch, landing batch and service mutation enters before beginning. A caller holding a section may finish; once closed no new caller enters. A single “paused” boolean is insufficient. Control/preference requests use separately counted control sections that may enter while work admission is closed; sealing the barrier at `stopping` closes those too, and shutdown waits for their count to reach zero. Long detached worker/review lifetimes are not sections; the claim/launch handshake is.

Drain proceeds as follows:

1. Persist `draining` with generation/request/target; close barrier. Keep `dispatch_enabled` unchanged. Let a tick already inside admission finish its claim/launch handshake. Reap, adopt and watch existing runs; launch no workers, reviews, gates, repairs or landing batches. Preserve completed worker results awaiting a future gate.
2. Wait for the **entire** existing landing call (including queued lease, batch gate, retries, cleanup, receipt and notification) to exit. A landing continuation may finish inside its already-held section. Wait for every open ledger `role=gate` run and launcher cancellation handshake to reach a recorded terminal result, plus an idle dispatcher tick. Gate completion may update ledger outcomes; starting the next platform gate remains fenced.
3. Stop admission to garden/tuner/discovery mutations; finish the current operation and park each service at an acknowledged boundary. Garden may park between rows and resume using its existing receipt mechanism. Watchdog remains alive through drain; a new live-WSL-run demand callback keeps its keepalive active even after the old `_wsl_needed` note expires. Drain also waits for active API admissions and mutation requests to finish; then reject new mutations with 503 and `Retry-After: 5`, except reload status/control and dispatch preference updates. These permitted updates finish before shutdown and never bypass the work barrier.
4. Require completed recovery, known process scan, no unresolved launches, no active Windows runner with `detached_in_job=true` or missing detachment evidence, no busy sections, no open gates, no live landing/service operation, and fresh participant acknowledgments for this generation. Do not infer safety from missing process/status data. Healthy Windows/WSL workers and reviews remain running; their run IDs and files are untouched.
5. Drain deadline is 900 seconds. On expiry, persist `blocked` and reasons, keep old hub serving/reaping, keep admission closed, and wait for an owner retry or cancel. Cancel reopens admission according to the **current** owner dispatch preference. No automatic timeout kill, lease deletion, synthetic receipt or task requeue.
6. Before shutdown, parent starts its own bounded WSL keepalive when WSL runs are present; it never kills the old watchdog's process or shuts down WSL. Persist `stopping`, reject further mutations including preference/control changes with 503, wait for admitted controls to finish, send the generation-bound stop command, stop both listeners/adapter loop, join every background thread (including the task-page probe pool), close ledger connections, then exit **75**. Stop probe admission, cancel queued probes and wait for running probes within the same shutdown deadline; timeout cannot report successful shutdown. Thread owners close their connections in their own `finally`; release dispatcher lock only after both dispatch and landing have stopped. No child-tree termination. Shutdown deadline 30 seconds; overrun blocks, leaving the existing PID alone.
7. Parent requires observed old PID exit and actual dispatcher-lock availability before spawning a replacement. It never starts two hub children or steals a lock. Candidate starts in `validating` with admission closed before app construction. Unknown supervisor protocol/identity refuses startup before opening the ledger.
8. Supervised main acquires the existing FileLock before Store construction and passes that already-held lock through create_app to DispatcherService (start must not acquire it twice). Candidate performs the read-only schema preflight above, opens the same compatible ledger, starts recovery-only dispatch, and binds the owner UI. New `GET /api/v1/hub/ready` returns 503 until ready, then 200 with protocol, runtime SHA, operation ID, generation, instance UUID, `ledger_schema`, fresh heartbeat counter (coordinator advances it every second after an acknowledged recovery tick and successful matching actual schema query, with dispatcher thread alive and last acknowledged tick no older than 45 seconds), recovery completion and dispatcher-lock ownership. Readiness uses a fresh in-memory heartbeat from this instance, not only persisted `_heartbeat`. This minimal readiness route accepts only a socket peer on loopback arriving at the owner UI port; it exposes no control or secrets and requires no bearer token. Parent checks loopback UI port against expected fields, matching schema, PID liveness and 15 continuous seconds of advancing heartbeat, within 60 seconds total. Missing WSL adapter for an optional listener is degraded, not fatal; unknown scans for actual open WSL runs block recovery and readiness.
9. Parent atomically commits the healthy active pointer and writes `committed`. Child opens admission only after matching that pointer/command. Resume services and dispatch according to the latest saved owner preference. WSL keepalive overlaps the new watchdog, then parent stops only the exact keepalive child it created. Reconnect browsers resync the page when instance UUID changes; do not rely on pre-restart SSE IDs.

## Failure and rollback

During validation there are no new gates, landings or service mutations. Adoption/reaping may persist legitimate existing run outcomes; keep those writes. If candidate import, bind, lock acquisition, recovery or heartbeat fails, close it cooperatively. A hung **validation-only** child may be terminated by its verified PID after 10 seconds because it has never received commit permission; never terminate its process tree. If old/new identity or validation-only status cannot be proved, block instead. Recheck PID exit and dispatcher lock before rollback.

Select the previous healthy immutable SHA through `check_recovery` and start it once with a fresh generation/instance, retaining the operation ID, using the same schema preflight and 60-second/15-second readiness rules. Source HEAD stays at B while A starts; candidate source eligibility is deliberately not used for fallback or committed-runtime crash recovery. This is automatic **runtime rollback**: main stays at the landed SHA, task statuses stay landed, and ledger/run files are never restored. Once fallback is healthy, persist `rolled_back`, disable auto and keep new-work admission closed while the fallback adopts/reaps. Owner retry selects a subsequent eligible repair tip, or cancel explicitly resumes the fallback. Quarantine the failed SHA until a new tip or explicit owner retry. If fallback also fails, persist `failed`, exit nonzero, and require owner repair; do not alternate SHAs forever.

Supervisor unexpected child exit: do not turn a crash into an approved drain. Restart the last committed runtime in recovery-only mode, adopt first, and keep admission closed until readiness succeeds. Startup crash budget: two attempts in ten minutes including one fallback; exhaustion latches `failed`. Task Scheduler relaunches must honor that durable latch. A supervisor restart acquires its lock, reconciles child PID **and creation identity**, generation and a live challenge-response; reattach a matching child rather than spawning. Unknown or unresponsive existing child/lock means blocked. Never signal an unrelated PID or trust a stale PID file.

For candidates, schema/dependency/protocol changes, changed interpreter, dirty source, insufficient disk or corrupted manifest stay pending for an owner-managed upgrade. Retained recovery uses its separate checks above; invalid retained contracts block rather than falling through to candidate checks. No ledger backup restore is part of rollback; forward migrations make that unsafe for adopted live runs. First supervised installation establishes a rollback-capable baseline; it cannot recover to pre-feature code lacking the protocol.

## Proposed schema and full worked example

No new ledger tables or migration. `hub_auto_reload` is an owner-only string setting (`"false"` default), projected from the parent-authoritative `auto_enabled` state. A dedicated toggle enqueues `action=set_auto` with `enabled:boolean`; the parent journals the change and the child mirrors the setting. Fallback mirrors it to false. Generic settings writes to reload-owned keys are rejected even for the owner; only the dedicated controller changes them. Reserve `hub.reload.` events and all `hub_reload_`/`hub_auto_reload` setting writes against bearer-token clients. Use dedicated owner routes for reload control; generic settings must not masquerade as reload requests. Existing owner checks are at `hub/api.py:188-199,306-312,379-389` and UI/CSRF middleware at `hub/app.py:60-70`.

Files under `<state>/hub-runtime/` use protocol `1`, UTF-8 JSON, atomic temp/write/fsync/replace, owner-only ACL inherited from the state root (existing installer ACL at `hub/scripts/Install-DroverHub.ps1:20-24`). Writers are explicit:

| Record | Writer and contract |
| --- | --- |
| `enrollment.json` | Installer only: protocol, source/common-dir/default-branch identity, absolute pinned paths, interpreter identity, `ledger_schema` (actual non-negative integer) and `required_schema` (independently derived release requirement), equal after successful read-only baseline probe, and bootstrap digest. |
| `releases/<sha>/manifest.json` | Parent after complete export: SHA, tree/content digest, protocol/run-format=1, `ledger_schema` and `required_schema` (equal to the verified enrollment pair, copied only after schema-blob equality), dependency/schema/bootstrap blob digests. Reuse verifies digest. |
| `requests/<uuid>.json` | Child or wrapper, create-once: `{protocol,id,key,action,source,operation_id,generation,instance,from_sha,target_sha,batch_id,auto,enabled,created_at}`. `action=request\|cancel\|retry\|stop\|set_auto`; `enabled` is boolean for `set_auto`, null otherwise; `source=landing\|owner\|reconcile`. The identity tuple is the observed target from parent status, not inferred from SHA. |
| `command.json` | Parent only: `{protocol,operation_id,generation,instance,request_id,action,target_sha,challenge}`, with `action=drain\|stop\|commit\|cancel\|probe`; `challenge` UUID is required for probe and null otherwise. Child echoes the probe challenge in child status on the next heartbeat. Parent reattachment requires that fresh echo plus OS creation identity. Child ignores stale operation/generation/instance. |
| `child.json` | Child only: `{protocol,operation_id,generation,instance,pid,creation_identity,runtime_sha,phase,ledger_schema,heartbeat_seq,challenge,recovery_complete,dispatcher_lock,barrier,blockers}`; `ledger_schema` is an integer from the actual pinned ledger, null before preflight or on query failure. `barrier` contains active sections/open gate IDs/landing and service acknowledgments, unresolved launches, WSL live-run IDs and participant generations. Supervisor verifies live handshake, never file existence alone. |
| `state.json` | Parent only: schema below; sole authority for active pointer, crash budget and phase. No secrets. |
| `journal/<sequence>.json` | Parent, create-once before matching state transition: `{protocol,seq,id,at,kind,data}`. State points to last applied sequence; restart replays any later complete records. Child mirrors into ledger events using `id` deduplication in a transaction, and emits SSE only as a hint. Parent does not access SQLite. |

State enums: `idle → pending → draining → stopping → validating → committed`; exceptional `blocked`, `rolling_back → rolled_back`, `failed`. Pending can cancel to idle; blocked can retry drain or cancel; rolled_back can retry replacement or cancel to resume fallback; failed needs owner repair/reset. `active` means last committed healthy release; `child` may be a validating different release. Healthy receipts include `manifest_digest`, anchoring retained content. Unknown version, invalid SHA, missing required field or damaged journal blocks without modifying the active pointer. Times are UTC RFC3339; elapsed deadlines use a monotonic clock. Sequence and generation are increasing integers; SHA values are full lowercase 40-hex; nullable fields are explicit.

**Operation fencing:** Parent assigns a new UUID `state.operation_id` to each accepted new reload/stop attempt and each accepted retry, even for the same SHA and same PID. Pre-drain tip coalescing retains that ID; fallback retains it but changes generation/instance. A new drain/retry or spawn advances generation; instance identifies one OS process and changes on spawn. Status exposes `(operation_id, generation, child.instance)`; no-operation ID is null. Every request carries the tuple observed by its producer. Cancel/retry require a non-null operation ID and exact match with current parent state, plus an allowed phase; stop/set_auto/request also reject an outdated observed tuple. UI forms preserve the tuple rendered with the action; the child must not restamp a delayed action with current identity. Parent first returns any stored exact-duplicate result (changed payload under that key conflicts), then checks new controls atomically in the reducer before any effect; child checks the resulting command tuple before applying it. A newer drain generation is accepted only when the parent's durable state names that operation/generation and this child instance; a cancel can only match its current operation/generation. Null is permitted for operation ID only when parent status has no operation, never as a wildcard. Generation/instance are mandatory.

Malformed/missing control identity is 422 at HTTP ingress. A well-formed stale tuple is 409 `stale_control` when detectable there; a race after 202 enqueue is durably rejected by the parent with that result and no barrier/phase/auto change. Reload GET/status reports the result by request ID. Persist key/payload/result: an exact duplicate returns its original result without reapplying; reuse of a key with changed payload is 409. Retired operation IDs never become valid again. A delayed cancel from operation X cannot resume operation Y, even when both target B; refresh and a new explicit owner action are required. Parent journal events carry operation ID as well as request ID.

**Schema evidence:** After read-only compatibility preflight and migration-disabled Store construction, `ReloadCoordinator.tick` reads `drover.ledger.db.schema_version(store.conn)` every heartbeat before publishing `ledger_schema` and advancing `heartbeat_seq`. Read error sets null, prevents heartbeat advancement and makes readiness 503; a successful query with a mismatched version reports that actual integer but also prevents heartbeat/challenge advancement and readiness. Parent issues a fresh probe and requires its challenge echo with an advancing sequence for the expected operation/generation/instance/PID creation identity; accept the sample only within 5 monotonic seconds of issuing that probe. Before candidate drain, again just before stopping, and throughout readiness, require integer `ledger_schema == enrollment.ledger_schema == enrollment.required_schema == release.ledger_schema == release.required_schema`; missing/null/boolean/mismatch is refusal. File mtime, persisted heartbeat and an old matching integer are insufficient.

After a proven drained exit 75, candidate spawn may use that final schema proof **only for the same handoff**: persist it in `state.handoff_schema` with operation ID, old generation/instance/creation identity, ledger_schema, challenge and heartbeat_seq; parent must have observed the fresh sample before stop and spawn within the 30-second shutdown window. It is permission for closed preflight, never readiness. Expiry, unexpected exit or supervisor restart invalidates this permission: use retained-runtime recovery instead. No-child initial startup/crash/fallback likewise uses retained recovery's closed preflight path. The new child always rereads the actual ledger before Store; no historical evidence authorizes migration, writes or readiness. Parent never reads SQLite, including after a crash.
