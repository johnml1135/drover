## Plain-language owner page

**Decide once.** Open **Decisions** on the website, or run `dv docket` after pairing your CLI. Each question shows the tasks it unlocks and the exact changes it will make. Pick an answer or write your own. Review the resulting changes and submit once. All the changes happen together, and every affected task shows your question, answer, name, and time. A worker can see “D1: yes, approved by owner” without finding the original conversation.

**Let routine work proceed.** In **Standing grants**, choose a lead or the unstick ladder, repositories, task kinds, sizes, risks, and a daily limit. For example: “docs, investigation, mechanical, and S/M fixes in these solo repos, up to 30 each day.” Each use appears in your daily digest. **Revoke** takes effect immediately for future uses. A grant cannot authorize external posting, installs, deletes, registry/system changes, or high-risk work.

**Approve an epic safely.** **Approve epic** shows included tasks and a separate excluded list with reasons. Tasks that post externally, install, delete, change registry/system state, or have high risk start excluded and need their own decision. Adding a task to the epic later does not approve it. You can also leave out any ordinary task.

**Move work.** Ask the lead to move a task; it uses the queue API and records why. The plan shows the resulting position, score, and “N tasks wait on this.” You can pin a task's lead-controlled override setting or forbid lead moves. Scores always come from the eight terms below. If a requested move conflicts with score order, the preview explains that limit and offers an explicit **Owner first (OP3)** action, which puts work above the ordinary queue without changing its score. The lead can select that action within your permitted band; a move request alone never silently sets an override or claims an unachieved position. Tasks at the same override level remain ordered by score, then task ID. **Stop the line (OP2)** takes the next eligible claim and freezes new work in its repo, or globally if selected. **Emergency (OP1)** takes the next dispatch opportunity on the best eligible seat, can use one extra parallel place, and bypasses a disk queue warning. Running work is never cancelled. Missing approval, prerequisites, unavailable seats, a hard resource stop, or your dispatch pause still show an explicit wait reason.

You can set any override. Agents may set OP3; emergency and stop-the-line changes by agents alert you immediately and expire after four hours unless you confirm them. The plan shows the timer. Landing or cancellation clears the override automatically. You can change or clear it at any time. Scores explain ordering; they do not give permission to perform an action.

**Keep useful work moving.** This machine has 20 logical cores and 64 GB RAM. Drover budgets 20 main units: heavy implementations or .NET builds/tests cost 4, small implementations cost 2, and mechanical work costs 1. Research, triage, review and grilling support have a separate lane of 10 light slots, normally using Haiku/Luna, so support can continue while the main budget is full. Live CPU load and model allowance can still delay admission. An emergency may add one worker beyond the main budget, including that worker's full unit cost; it never starts a series of extra workers.

**Keep branches current without constant retesting.** When main changes, Drover checks open task branches at most once every 15 minutes per repo, using Git and no model tokens. Disjoint files are **clean** and need no repeat build or test unless that branch still owes a test from an earlier dirty integration. Overlapping files that merge successfully are **dirty** and get one build/test immediately before merge. Rebasing or a later clean classification cannot erase that obligation. A **conflict** creates a small Luna resolution task. Solo repos can update idle task branches mechanically. In team/PR repos, including FieldWorks, liblcm and machine, the periodic check only classifies: clean branches stay untouched, and a conflict needs your explicit approval for that PR before main is merged into its branch. Those PR branches are never rebased or force-pushed. GitHub CI remains the PR check. Each solo landing batch gets one main gate; a red result pauses further landing and bisects the batch to find the culprit.

## Authority and invariants

A principal is authenticated server-side, with stable identity and role. Do not infer owner authority from a payload's `actor`, a token's spelling, comments, free text, worker output, or a lead's report of what the owner said. T-8i/D5 supplies a separate expiring, revocable owner credential through explicit browser pairing. Keep web CSRF protection. CLI uses the hub API, never SQLite or spoofed UI headers; no owner credential enters a worker brief/environment.

“Lead” below denotes the owner's designated coordinating principal, not a new worker role. Scoped lead and unstick capabilities are bound to authenticated identities; a generic worker bearer does not become a lead because it supplies that name.

A standing grant **never** covers posting PRs or responses (or other external publication), package installation or dependency addition, deletes (files, branches, worktrees, records, or remote resources), registry changes, system-state changes, or `risk:high`. Unknown or mixed effects fail closed. An innocuous kind/title is not evidence of harmless effects. Owner approval of exceptional work must specify that action's target and bounds; it cannot bypass repository/platform rules or authorize a forbidden operation.

Task approval and action authorization are separate. Even an owner-approved task cannot publish or install without the specific effect authorization required by its action service. This spec does not widen the PR spec's publication trust contracts; these grants cannot be used as PR trust entries. Scoring, a queue move, an override, or approval of an epic's ordinary subset never authorizes an excluded effect.

## Layer 1: decision bundles (land first)

### Bundle contents and lifecycle

A docket item is the unit of decision. Attach one immutable versioned bundle to the existing docket/owner-answer item, containing:

- Stable question ID and displayed number, full question/context, option IDs and labels, free-text permission, required fields, source spec/task references, and the proposed recommendation.
- Exact task membership with role (`unlocks`, `edits`, or `context`); all tasks changed or unlocked must be linked to the answer. Context-only tasks receive a clearly non-authorizing link.
- For each option, typed effects: explicit task approval, dependency add/remove, scope replacement, priority change, handoff text update, and any separately authorized queue/override action. Include before/after values, target revisions, and expected approval/hold predicates. No executable shell fragment.
- Approval-relevant fingerprints covering repo, kind/type version, risk, size, write/effect capabilities, file/read scope, acceptance/goal, dependencies, and action targets. Hash canonical JSON; hash is a binding, not a substitute for authorization.

Lifecycle: `draft -> open -> applied`, with `superseded`/`withdrawn` exits before application. An edited question, option, membership, or effect creates a new revision and supersedes the old proposal; it never rewrites an answered version. Reject expired or superseded forms with a diff and reload path. A decline/“no” is itself an answer with its specified effects (often no approvals); it must not accidentally approve the whole membership.

Support both stable option choices and full free text. Store the original text, without interpreting it as code or granting implied permissions. Structured supplemental text, such as a bounded path or handoff sentence, is validated against the versioned answer schema and rendered into an exact effect preview. If arbitrary text changes the proposed effects (“yes, except task X”), save an answer draft and have the assessor/lead propose a revised typed bundle. The owner sees and submits that final answer and effect set together. No LLM interpretation may run after final submit and silently alter the approved effect set. A free-text answer whose predeclared effect is simply “record these directions” may commit immediately; it unlocks only explicitly listed work, never guessed approvals.

### One transaction, one decision

Both website and `dv docket` call the same action service:

1. Authenticate principal and action, validate `expected_revision`, bundle hash, task fingerprints/revisions, grant if applicable, and idempotency key. Acquire the hub write transaction and recheck all predicates there.
2. Validate the complete typed effect plan, including dependency cycles, authorized scope/priority changes, task states, handoff length, exclusions, and unrelated holds. Grant-backed effects are limited to approval and releasing the exact approval hold; edits to scope, dependencies, priority, or handoff require an owner bundle or separate existing authority.
3. Persist one immutable decision record with the submitted question/options snapshot, answer, principal, authority basis, timestamp, bundle revision/hash, and full effect receipt. Attach it to every affected task. Apply **all** changes and approval stamps, then release only holds whose exact decision requirements this record satisfies. Preview hashes bind both the before-state preconditions and the computed after-state; approval links bind the **after-effect** fingerprint, so approved scope/dependency edits do not immediately invalidate their own approval.
4. Recompute eligibility through the existing state kernel. Approval does not force `ready`: incomplete dependencies, other holds, cancellation, stale approval, and existing execution state still apply. Do not requeue a running/gated/reviewed task to “unlock” it.
5. Append the canonical decision event, per-task references, and durable notification/assessor outbox entries in the same transaction. Commit, then publish SSE/inbox updates. No network call or model assessment is inside the transaction.

Any invalid member rolls back the answer, links, task edits, approvals, counters, events, and outbox. A retry with the same principal/request key and identical payload returns the original receipt; a different payload with that key conflicts. Two channels racing on the same revision produce one applied decision and one stale response, never two approvals. A post-commit delivery failure is retried from the outbox, not by reapplying the answer.

Keep questions and their task-types owner-answer mappings as a compatibility facade. Existing answer endpoints delegate here when a bundle is present. A multi-question docket round can contain several bundles; each explicit bundle submit is atomic. A “submit round” operation must preview a combined conflict-free bundle if it promises all-or-nothing behavior; it cannot disguise sequential partial commits.

### Worker and reviewer evidence

Task detail, API, reviewer context, fresh briefs, and resumed-worker context include a **Decisions applying to this task** section before trimmable discussion. Show decision ID, question ID/number and full relevant question/answer, who/when, authority (`owner` or `grant G-x used by principal`), task-specific effects, constraints, applicability fingerprint, and supersession/revocation status. An assessment ID is distinct from an owner decision ID. Preserve complete text in the task projection; if the brief cannot fit required evidence, use a dedicated readable decision artifact and pause launch until it can be supplied. Do not silently truncate the authorizing answer.

Launch/relaunch resolves current requirements from ledger links rather than searching transcripts. Resume delivers a new decision revision before dependent work continues. If T-bh cannot reliably inject into an active session, finish unrelated authorized work or hand off to a fresh brief; do not assume the session saw SSE. A worker reporting “approval missing” triggers a requirement lookup; a matching current record is supplied, while a mismatched/absent record creates one deduplicated docket issue. A lead assertion alone cannot satisfy the lookup.

T-bl assesses simple instructions against the task's outputs and exact decision effects: for example, “use the approved PyYAML approach, only this scope.” It records satisfied/violated/unknown plus evidence. Assessment cannot reinterpret an answer into broader authority, override an owner refusal, or manufacture an approval. Violations/unknowns enter the existing unstick/docket flow, with the original decision visible.

## Layer 2: standing grants

A grant is a scoped, revocable approval delegation to a named lead or the unstick ladder. It is not an owner credential. It has owner issuer, grantee, registered repo allowlist and collaboration mode, task kinds/type versions, size allowlist, risk allowlist (low only in v1), explicit allowed actions (`approve-task` and its exact approval-hold release), daily cap, effective/expiry times, and revision. Predicates are conjunctive; alternatives are explicit clauses, not accidental products. The example grant is `(kind in docs/investigation/mechanical) OR (kind=fix AND size in S/M)`, AND named solo repos, low risk, no forbidden effects, at most 30 task-version approvals per owner day. Each clause also states its size allowlist.

Use registered repo IDs and a server-owned collaboration classification; missing solo/team information makes a solo-only grant ineligible. Effect classification derives from pinned task/action metadata, including composite capabilities. Missing metadata excludes the task; neither the lead nor worker can label effects harmless to gain approval. Reclassifying or changing approval-relevant inputs invalidates the approval fingerprint and requires a new decision. If new forbidden effects appear, hold before execution; recheck at admission and effect execution.

For a use, atomically recheck active grant revision, grantee, current task fingerprint/predicates, and daily remaining cap, then create a grant-attributed decision and increment usage. Count task-version approvals, not API requests: a bundle approving 8 tasks consumes 8. Duplicate retries consume zero extra; already-approved unchanged tasks consume zero and return their original receipt. Reapproval of changed work consumes another unit. Multiple simultaneous uses cannot exceed the cap; usage sums across revisions of the same grant/day, so an edit cannot reset it. Different grants cannot be combined to satisfy one task's missing predicates.

A day is a calendar day in the owner's configured IANA timezone, fixed into each grant revision (America/New_York for today's example). Store its UTC start/end and timezone; daylight-saving days are not assumed to be 24 hours. Changing timezone cannot reset the current cap; owner replaces the grant for the next day. Revocation and use serialize in the same ledger transaction: no use committed after revocation is valid. Revoke is one click with no new approval prompt. It prevents future uses; existing valid task approvals retain their exact bounds and audit links. The owner can separately hold/revoke a task approval, and a suspected compromised grant can offer an explicit reviewed list to hold, without stopping running processes implicitly.

Every use and refusal is auditable. The daily digest groups uses by grant, repo, and task with decision links, remaining cap, failures, and excluded work. Immediate revocation invalidates caches for future grant uses; each use checks the authoritative current revision. A claim under an existing approval validates its fingerprint and that its grant was valid at the recorded use, without retroactively invalidating it on later grant revocation. Grant expiry behaves as revocation for future uses. Widening, renewal, higher caps, and a replacement grantee are owner-only new revisions, with no implicit renewal.

## Layer 3: epic approval with exclusions

Preview an immutable manifest of the epic's currently proposed/draft tasks, each fingerprint/revision, ordinary included subset, owner-optional omissions, and mandatory exclusions with **all** reasons: external posting, installation/dependency change, delete, registry/system change, high risk, or unknown effects. Never derive permission from epic membership alone. Already-approved tasks appear as unchanged context, not fresh approvals; cancelled/landed tasks are not resurrected.

Default all mandatory exclusions to unselected. They cannot be selected through the bulk action: open an individual decision with exact exceptional effects instead. The owner may omit more ordinary tasks. Show totals, dependency consequences (an included task may still wait on an excluded prerequisite), and changed task details before submit. T-8j applies the exact ordinary subset as one decision transaction. Any changed member/epic membership invalidates the manifest and returns a refreshed preview; a task added later needs another approval. An empty included subset is a no-op receipt, not approval of exclusions.

An epic is a convenient way to prepare a bundle, not a standing grant over future tasks. The lead may prepare it but cannot approve it with a bearer. A named grantee can approve matching individual tasks through normal grant use with per-task cap consumption; it cannot call epic approval to skip exclusions or caps.

## Deterministic ranking

### Eligible work and the comparator

Replace `ready_tasks`' old sort with exactly:

`(effective_override_order, -score, task_id)` where OP1=0, OP2=1, OP3=2, none=3; task IDs compare as canonical ASCII strings.

There is no additional priority, epic rank, manual rank, pressure, size, insertion-time, or seat-dependent tiebreaker. Eligibility remains separate: current approval, valid dependencies, holds, scope conflicts, platform/repo policy, and OP2 freezes are enforced before claim. Store a breakdown for all nonterminal tasks so the owner can inspect blocked and finishing work too. Gated/reviewed work continues through gate/review/landing queues; do not start a second worker just because its score is high. Finish-first informs any shared admission choice among already valid stages, preserving stage prerequisites and the landing queue.

A pure function `score_task(task_snapshot, graph_snapshot, policy_snapshot, as_of) -> breakdown` reads no DB, clock, live seat usage, network, randomness, or mutable config. The hub assembles all inputs from one ledger snapshot, including allowance evidence in `policy_snapshot`. Time and allowance readings are explicit ledger evidence. Use 50-digit decimal arithmetic with round-half-even for intermediate calculations, then round each term to 0.01 points using round-half-up; sum rounded terms, then clamp/round score S to `[0,100]`. This is the sole comparator score: manual requests, queue positions and override changes never replace it or adjust a term. Compute `log2(1+W)` as decimal `ln(1+W)/ln(2)` at that precision; pin the algorithm in the ranking policy version and prohibit intermediate binary floats. Retain raw operands and term results for replay. Pure-function tests define fixed reference values.

### Score policy v1

`S = clamp(P + U + F + E + A + L + C + R, 0, 100)` for every task in every override stratum, including after a lead move. There is no second queue score, manual offset inside E, position-to-score projection, or additional ordering pass. Changes to ledger inputs recompute these same terms; changing this ranking policy requires the separate owner-approved lesson/replay process.

| Term | Definition and proposed v1 defaults |
| --- | --- |
| P, up to 35 | P0=35, P1=22, P2=10, P3=0. Existing P4 also scores 0 until owner reclassification; preserve its label |
| U, up to 25 | Priority-weighted unique transitive blocking dependents plus active T-bg stuck-task links. Let `W` be the sum of P0/P1/P2/P3/P4 weights 4/3/2/1/1 over their union, excluding self and landed/cancelled/archived tasks. `U=min(25, 5*log2(1+W))`. Follow only blocking dependency edges; traverse cycle-safely and deduplicate diamond paths and tasks also linked by T-bg |
| F, up to 12 | Current gated or reviewed evidence for the exact current work SHA=12; otherwise branch exists AND attempts>0 gives 8; otherwise 0. Never add 12+8. Stale gate/review evidence gives no 12 points |
| E, up to 10 | Among open epics sorted by `(rank,id)`, ordinal 0 scores 10, ordinal 1 scores 9, sliding to 0 at ordinal 10; no epic scores 0. Add 2 for an explicitly task-named active owner docket decision (not every member of an epic bundle), then `E=clamp(epic_points+docket_points,0,10)`. Manual moves do not alter this term |
| A, up to 10 | `0.7 * min(14, max(0, elapsed_seconds_since_created/86400))`. Thus the specified 14-day cap is 9.80 points; do not round it up to 10 or reset age on a move/retry |
| L, up to 8 | `8 * p_first_pass[kind,size]` from a pinned harness-derived policy table. Use fixed seed priors below until sufficient harness evidence supports an owner-approved update; no online per-claim learning |
| C, down to -6 | S/M/L base cost 0/-2/-4, multiplied by `(1 + 0.5*q)`, with ledger allowance pressure `q` in `[0,1]`. Thus L at full pressure costs -6 |
| R | High risk=-2, low risk=0. Risk penalty never confers approval |

Seed first-pass probabilities (S / M / L): docs `.90/.85/.75`; investigation or research `.85/.75/.60`; mechanical `.95/.85/.70`; fix `.80/.65/.50`; implementation `.75/.60/.45`; review `.85/.75/.65`; unknown/custom kind `.50/.50/.50`. These are explicit priors, not claimed measurements. Persist table version and sample counts; future tuning replaces it only through the lesson process below.

Allowance pressure uses the latest valid ledger reading per enabled worker seat, chosen by `(observed_at,id)` at or before `as_of`. Normalize the recorded used fraction to `[0,1]`; q is the maximum among those readings. Missing readings, no enabled seats, or any enabled seat reading older than 15 minutes yields q=1 conservatively. Use a stable seat list from policy; disabled seats do not contribute. No task's score depends on whichever seat is queried first. A new valid reading creates a new generation, never alters the old replay inputs.

The plan's **“N tasks wait on this”** counts unique active stuck tasks linked by T-bg, independent of W's priority weights. Each link has evidence, not a lead-supplied free counter. Terminal/resolved links stop counting; duplicate or cyclic links cannot inflate U. Dependency-only unblock counts appear separately. U may put a lower-band systemic fix ahead of ordinary higher-band work, without moving its epic or changing its P label. This is an automatic score boost, not an OP override or an unconditional precedence rule: other terms and override levels still apply.

Golden example: P1, union containing one P1 dependent (W=3), branch+attempts, no epic/docket, age 10 days, docs/M, q=0, low risk, no override gives `22 + 10 + 8 + 0 + 7 + 6.80 - 2 + 0 = 51.80`. A new P0 task with no dependents/epic, age 0, mechanical/S, q=1, low risk gives `35 + 0 + 0 + 0 + 0 + 7.60 + 0 + 0 = 42.60`. OP3 orders that second task ahead of the first despite its smaller score. Non-power-of-two fixtures include W=2 giving U=7.92 and W=4 giving U=11.61; tests also fix boundary rounding cases.

### Lead reorder, bands, pins, and comparator limits

The owner-set move band defaults to the task's P label and registered repo; only the owner changes band assignment/rules or grants cross-band queue control. A lead move names a before/after neighbor in the same band, with a nonempty reason, expected queue revision and the lead queue capability. The action cannot change the task's epic, P label, score inputs, dependencies or approval. Position means the requested relative order, not guaranteed adjacency or a reserved claim slot; eligibility still applies.

The prescribed comparator limits ordinary reordering: at the same override level, a lower-scoring task cannot be placed ahead of a higher-scoring task, and task ID resolves equal scores. An arbitrary persistent manual order would require a ranking-policy change the owner has not approved. V1 preserves the approved comparator and offers the already authorized OP3 action explicitly when a requested move needs precedence above ordinary work. Neither a stored rank nor a topological sort may override score order. Do not add a hidden E adjustment or substitute queue-position numbers for S.

1. Preview computes current order from `(effective_override_order,-S,task_id)` and validates the band, authority and owner controls. A move with no override action succeeds only if the requested relation already holds; return an explicit `already-in-order` no-op receipt. Otherwise return `score-order-conflict` with no task/ranking mutation, the two breakdowns and permitted alternatives. A denial is audited, never logged as a successful reorder.
2. To move above ordinary work, the caller explicitly selects `override=3` in the preview/submit, or uses the existing OP3 action. `dv move T-x --before T-y --override 3 --reason ...` previews and applies that OP3 change through the same override service as `dv op`; a plain `dv move` never sets it implicitly. The ordinary band limit and pin/forbid checks apply to lead moves through either endpoint. Show that OP3 may also move the task ahead of ordinary work outside its band; band permission restricts which task the lead may move, not OP3's global precedence. An owner may forbid this lead action for a task/band/repo.
3. Recompute the comparator order with only the proposed override change, using the same ledger operands and `as_of` for the before/after comparison. Later ageing or new ledger evidence uses the normal generation process, not a move-specific score adjustment. Submit succeeds only if the requested relation holds after that change. For example, OP3 cannot move a lower-scoring task before a higher-scoring OP3 task. Reject that request without setting any override, and explain the available owner actions. OP1/OP2 require their separate explicit action, reason, alert and expiry rules; never escalate automatically to satisfy a move.
4. Apply the allowed override change, ranking generation and reasoned `queue.reordered`/`override.set` events atomically. The receipt shows requested relation, before/after override and positions, unchanged S and eight-term breakdowns, affected ordering, policy/revision and actor. A stale revision, missing authority, pin/forbid violation or unachievable relation returns a no-mutation denial; retries return the same receipt. Do not rewrite scores for the moved task or any other task in its override stratum.

A reasoned reset explicitly previews clearing the selected lead-authored OP3 overrides in the band, using the override service. It validates all affected pins/forbids atomically, never clears an owner-set/confirmed override, and reports the resulting comparator order. It does not reset scores, age, epic rank or task IDs. New tasks join by the comparator, without append-only manual membership. Owner pin/forbid rules apply to lead changes and reset through every API alias; pinning protects the chosen override setting from lead queue actions, not an absolute position as U, age, eligibility or other overrides change. OP1/OP2 emergencies retain their approved authority/expiry behavior and log any crossing of a queue pin. The owner can explicitly change these controls. A request for persistent arbitrary order within one override level remains a proposed owner ranking-policy decision; this spec does not activate one.

### Ranking generations and policy tuning

Persist one complete ranking generation at a ledger watermark and `as_of`; recompute on relevant task/dependency/unstick/docket/queue-policy/override/policy/allowance events and at a persisted hourly ageing tick. Apply expires-at checks at claim time even between ticks. Claim transaction checks input revisions/generation validity; stale generation is recomputed before selection. UI/API/CLI return the same generation, `as_of`, policy hash, operands, score, and wait reasons. They do not recalculate independently in JavaScript or terminal code.

Weights and tables live in validated config and the versioned policy snapshot. E-v may propose a lesson with evidence and replay old/new policies against saved generations, showing changed first picks, starvation, throughput, first-pass outcomes, and risk distribution. Only an owner action activates a new version after replay and review. No automatic weight tuning, silent config override, or model output writes a live score. Existing runs retain their pinned execution policy; claim ordering uses the current approved ranking policy.

## Override priority and dispatcher behavior

An override is scheduling authority only. Setting one does not approve a task or erase a hold. Require a reason for every set/change/clear, show actor/time/expiry, and clear automatically on landed/cancelled. The owner can set any level from website, docket answer, or `dv op T-x <1|2|3> "reason"`, select OP2 repo/global scope, confirm an agent override, or clear it.

Agents/lead may set OP3 on tasks they can act on without a standing approval grant. They may set OP1/OP2 only with a reason and a durable immediate website inbox/SSE alert committed with the override. Default repo scope for OP2; global must be explicit and prominent. Expiry is no later than four hours after the first escalation for the same unresolved incident; the server binds that incident to the task/escalation chain, so a new request key or switching OP1/OP2 cannot renew it. Agents cannot keep resetting the timer, lower/clear an owner's override, confirm themselves, or replace an owner-confirmed level. Owner confirmation records a new revision and chosen duration (unbounded allowed). OP3 has no automatic four-hour limit unless explicitly set. An expired override is ineffective even if the cleanup job has not run. T-bm exposes confirmation and expiry in the docket; external notifications require their existing owner-enabled adapter.

| Level | Admission and claims |
| --- | --- |
| OP1 emergency | Evaluate before ordinary resource-queue/capacity early returns. At the next dispatcher opportunity, choose the highest ordered **eligible** OP1 and the best eligible seat under current routing/placement policy (stable configured seat order for equal routing outcomes). May admit **one extra worker total**, not one per OP1; its full cost may exceed the 20-unit main cap as defined below. Never cancel/preempt running work |
| OP2 stop the line | Highest eligible permitted OP2 target claims before OP3/ordinary work; overlapping-freeze rules below select the permitted target. Activates a durable new-claim freeze over its repo by default, or global explicitly, from set time until landing, cancellation, expiry, or authorized clear. Running work and all gates/reviews/landing continue |
| OP3 owner first | Ahead of every ordinary task, within ordinary capacity/resource admission; no freeze and no extra place |

OP1 bypasses only the **disk queue hold** (soft disk queue warning) and ordinary main capacity for one extra worker. Before weighted admission activates, this is the legacy parallel cap +1 worker; afterward it is the unit-cap exception below, not +1 unit. It does not bypass a hard disk stop/unknown hard-stop reading, other resource holds, physical seat limits, allowance admission, approvals, dependencies, scope conflicts, platform/repo rules, or the owner's dispatch pause. Check/report current disk headroom before heavy work. If the best eligible seat cannot launch safely, use the next eligible seat per routing policy; if none exists, show a precise OP1 wait reason and alert without cancelling work. Persist/adopt the single emergency capacity lease across restart; multiple dispatchers/retries cannot each take +1. Once ordinary capacity becomes free, absorb the emergency worker into it.

An active OP2 freeze blocks *new worker claims*, not completion stages or existing workers. OP1 has precedence through an OP2 freeze and logs that bypass; OP3 cannot cross it. For multiple overlapping OP2 scopes, the highest comparator-ordered active OP2 is the permitted target in the overlap; freezes do not block their own permitted target. Independent repos can each proceed under their own nonoverlapping OP2; a global freeze covers every repo. A blocked/unapproved OP2 still freezes its scope and shows what it waits on; its ordinary prerequisites do not silently become exempt. Use existing running work to finish, a specific OP1 escalation, or owner change/clear to resolve a deadlock. Dependency and resource eligibility still apply to the permitted target. Failed gates, review, or a merely completed worker do not clear OP2: only actual landing or another listed termination does.

The freeze is derived from current ledger overrides at each atomic claim, not an in-memory flag. Set/claim races serialize; claims committed before the freeze remain running work. On restart restore freezes, expire deadlines, reconcile emergency leases with adopted runs, then admit new claims. Keep gates/reviews/landing schedulable during an OP2 freeze even when worker capacity is exhausted; retain their existing resource requirements. Every deferred override displays its blocked reason rather than repeatedly attempting launch.

## Weighted parallel capacity and the light lane (W1, W3)

Replace the flat `parallel_cap=4` admission limit with a main budget of **20 weighted units**, configured with cost rules. CPU during .NET builds and model allowance are the observed constraints on this 20-logical-core/64-GB machine; RAM normally does not bind, but its hard-stop tracker remains active. Units are admission reservations, not a claim that each worker occupies exactly that many cores.

| Main work class | Units reserved while active |
| --- | --- |
| Any .NET build/test, or M/L implementation (including fixes) | 4 |
| S implementation/fix without .NET build/test | 2 |
| Mechanical work without a heavy effect | 1 |

Apply the highest matching cost once, rather than adding rules. Other non-light work defaults conservatively to 4 until an owner-approved rule classifies it; title/model/size alone cannot downgrade a declared .NET effect. Task stage and registered build/test metadata determine the class. A worker which can build .NET reserves 4 for its whole run. A separately scheduled gate or dirty-branch retest reserves its own 4 only after the worker lease is released; concurrent processes must each reserve capacity. Mechanical Git classification/integration uses 1, with bounded sequential scans, no model, and no independent build fan-out. Pure ledger projections need no worker lease.

Reservation and task claim form one atomic admission operation. Normal main work requires `active_main_units + candidate_units <= 20` and all resource/platform/policy checks; model-backed work additionally needs an eligible seat and allowance. Mechanical Git services and gates reserve units without consuming a model seat or allowance. Process exit or confirmed failed launch releases the reservation exactly once; disconnect/lease timeout alone does not free a still-running process. Restart adopts leases by run/process identity before new admission. Policy reductions let existing work finish and stop further admission until within budget; no process is killed. The legacy flat cap ceases to be an additional global limit after activation; explicit per-seat limits still apply.

The comparator remains exactly `(override level, -S, task ID)`. Admission may skip an ineligible or non-fitting candidate and record its wait reason; it does not recalculate S from current CPU usage or create a second queue sort. Finish stages share the main budget when heavy. Reserve newly freed units for the highest ordered eligible waiting finish stage before starting new ordinary work, so gates can complete under OP2 as workers release capacity. OP1 remains first. This stage-admission rule does not re-launch a gated task as a worker.

**OP1 with weighted units:** use ordinary capacity if it fits. Otherwise one globally serialized emergency lease admits one additional main worker at its full configured cost `w`, provided existing main usage is at or below the cap. Total may reach `20+w` (24 for the default heavy worker); there is no +1-unit limit, and no second overflowing worker while the lease is live. Do not use the exception to launch extra gates or retests. A light-kind OP1 may use this one main emergency worker if its light lane is full; its recorded main cost uses the configured rules, not a hidden eleventh light slot. Keep ordinary admissions at/below the main cap including the emergency run; absorb it when total fits again. Reconcile policy changes against the recorded lease/cost without cancelling work or granting another exception.

The **light lane has 10 slots**, separately configurable, for research, triage, review and grilling support routed to configured Haiku/Luna seats. Each light run occupies one slot and no main units. It continues when all 20 main units are reserved; evaluate it independently of a main-cap early return. It still requires allowance, an available seat and resource checks; OP2 freezes apply to new light task claims in scope, while reviews of existing work continue. Reviews requiring a .NET build/test use main capacity for that heavy stage. A light run cannot start builds or implementations opportunistically: hand off to a main stage and obtain its reservation first. A full light lane cannot silently spill into main or vice versa, except the explicit OP1 emergency case.

Keep the live load tracker in front of both lanes. Proposed initial build-heavy `queue_per_core=1.0` tightens the current 2.5 threshold; retain `hold_per_core=3.5` initially, with validation that queue < hold. These are proposed defaults, not additional W decisions. A CPU queue verdict can delay even OP1; its exemption is disk queue only. Allowance admission remains independent of unit availability, and light seats get no exemption from account reserves. Resource responses must identify the tracker and affected lane instead of collapsing “main budget full” into a global stop. Check disk before every heavy stage; never treat spare RAM as permission to ignore CPU/disk pressure.

Config carries `main_units=20`, the class weights 4/2/1, `light_slots=10`, light routes, and load thresholds in a versioned capacity policy. Existing tuner writes to `parallel_cap` must stop controlling this policy after activation. E-v uses per-run/stage peak CPU and RAM, sample coverage, queue delay, allowance and throughput to propose weights/caps/thresholds. Normalize CPU measurements with the host core count, preserve raw evidence, replay saved admission streams, and require owner approval to activate a lesson. No live automatic adjustment from a model or a single noisy sample.

## Continuous mechanical branch maintenance (W2, W4)

### Classify on main movement, without model calls

After an observed main advance, mark the repo pending: use local main in solo repos and the registered remote-tracking target in team/PR repos, never an owner's unpushed local main for a PR. Reuse the existing authorized ref-observation/sync service; classification does not grant fetch or publication authority. Coalesce subsequent advances and scan the latest main SHA **at most once per 15 minutes per repo**, persisting the last scan time across restart. The first eligible scan may run immediately; a new main during the interval schedules one trailing scan, not one per commit. Classify every open task branch, including running branches from captured refs, with zero model tokens. A scan consumes mechanical capacity; if admission delays it, expose the lag. An unchanged `(main SHA, branch SHA, algorithm version)` reuses its result. At landing, cheaply validate/reclassify the exact candidate tuple if refs moved; this targeted correctness check is separate from a periodic all-branch scan and starts no background retest.

Compute the merge base, the changed-path sets from it to main and to the branch, and a non-mutating Git merge result. Include renames' old/new paths, deletes, type changes and submodule paths in overlap detection. Compare the refs again before storing or acting; if either moved, mark the observation stale and reschedule. Git errors, missing objects or ambiguous bases produce a visible diagnostic/hold, never a fabricated clean result.

| Classification | Definition | Solo-repo action | Team/PR-repo action |
| --- | --- | --- | --- |
| clean | No file/path changed both on main since merge base and on the branch; Git integration succeeds | Mechanically update an idle task branch as below; merge through landing without another build/test merely for main movement, unless a carried retest obligation is pending | Classify only; leave branch alone; no periodic rebuild/test |
| dirty | Changed paths overlap, but Git merges without conflict | Mechanically integrate an idle branch; defer its single rebuild/retest until immediately before landing | Classify only periodically; rebuild/retest once immediately before merge on the exact candidate; GitHub CI remains authoritative |
| conflict | Git positively reports an integration conflict | Create one deduplicated small Luna resolution task for the captured conflict | Prepare the same task, held until explicit owner approval for this PR; resolution merges main into the PR branch, never rebases or force-pushes |

Classification is mechanical; only conflict resolution uses a model. The resolution task is S, inherits relevant scope/risk/effects and the source task's decision records, and needs applicable task/action approval. A risk:high conflict cannot be approved by relabeling it small or by a standing grant. Deduplicate on PR/task and input SHAs; a changed conflict updates the proposed work rather than creating a stream of identical workers.

### Safe branch updates and just-in-time retesting

In solo repos, a dedicated service may mechanically rebase/replay idle task commits onto captured main, or record an equivalent integration candidate, under the enabled repo policy. This is the continuous solo rebasing contract; final landing still goes through the fast-forward-only landing queue. It never pushes. Classifying a running branch is read-only; defer ref/worktree updates until its worker/reviewer releases an exclusive branch lease. Never overwrite owner edits, another session's index/worktree or uncommitted files. Prepare candidates in a service-owned isolated worktree, then compare-and-swap the original branch SHA under the lease; mismatch leaves it unchanged. No worker receives permission to change another worker's branch.

In team or PR repos (explicitly FieldWorks, liblcm and machine), periodic maintenance **only classifies**. No branch ref, checkout or remote is updated by that scan. Clean branches are left alone. Conflict resolution requires an authenticated owner decision bound to the specific PR, captured main/branch revisions and merge-main action; a materially changed target needs a refreshed preview/decision. Use a merge commit from main into the branch, preserving published history; never rebase or force-push. Publication of the resulting commit remains a separate explicitly authorized action under the team-PR spec. An unknown collaboration mode fails closed to classification-only. GitHub CI on the exact PR candidate/base remains the real check; local testing cannot manufacture a green CI result or authorize merge.

A clean classification **with no unsatisfied retest obligation for the candidate** carries existing exact-SHA task gate/review evidence forward as **provenance plus a structural transport receipt**, not as a newly passed gate for the rewritten SHA. This policy exception must be implemented explicitly at the gate/landing boundary before enabling solo updates; the current exact-SHA checks cannot simply be disabled. A resolution or any nonmechanical content change requires its own normal gate/review. Classification never waives repository-mandated PR checks or a task's initial tests.

A dirty observation creates or updates a **persistent retest obligation** for the stable task/branch lineage in the same transaction as the classification. Re-observing the same classification/input tuple is idempotent: it cannot increment the required revision or reopen a satisfied matching candidate. Only new dirty integration evidence advances that revision. Before any mechanical ref update, durably link that obligation to the integration and its output branch. Persist an integration intent before Git compare-and-swap; recovery reconciles its actual ref and retains the obligation before admitting landing. A crash, rebase/replay, merge-base change, later clean classification, restart, branch rename or policy rollback must not remove it. Unknown lineage/provenance holds landing for reconciliation rather than assuming clean. A classification answers what overlaps *now*; it does not answer whether earlier overlapping integration was tested.

At landing, evaluate both the current classification **and carried obligations**, before considering a clean transport exception. Dirty work or an unsatisfied obligation requires a build/retest **once, immediately before merge**, on the prepared integration tree with pinned gate policy/platforms. Only a successful receipt matching the current exact candidate key and covering the obligation's required revision marks it satisfied. Record satisfaction atomically with receipt attachment; a clean result, an old branch gate, or a successful mechanical rebase cannot clear it. Retain obligation history and its satisfied key until the task is terminal. If main/branch/tree/gate policy/platforms change before landing, the old receipt no longer satisfies the obligation: mark it pending again and test the newly selected candidate once. Landing rechecks this key under its ref lease, so a ref race cannot use a stale success. Do not retest on each main tick, classification, lease renewal or dashboard read. Persist a durable retest job/receipt keyed by exact `(main SHA, branch SHA, integration tree, gate policy/platforms)` and the obligation revisions it covers; retries of the scheduler reuse it. A red result holds that candidate without automatic repeat runs; an explicit retry is logged. A changed candidate invalidates the receipt and gets one new just-in-time test when selected for merge, rather than immediately testing every open branch. Never schedule a duplicate test for the same candidate key merely because the branch was mechanically updated; a genuinely changed key follows the obligation/retest rules above. Team PR checks required by GitHub still apply and are separately identified in cost reporting.

A timed-out, interrupted or lost gate attempt is **not a successful receipt**, even when no test failure was printed. Preserve the pending obligation and candidate hold; record the attempt outcome separately from an assertion failure, with command/platform, candidate key, start time, last-output time and available log reference. Recovery first reconciles the attempt's process identity and capacity lease. An authorized explicit retry creates a new attempt under the same candidate job and keeps the earlier evidence; a scheduler restart alone cannot duplicate a possibly running test or mark the obligation satisfied. The same rule keeps a post-batch main gate pending/held after a timeout, so the next batch cannot slip through.

### One main gate per landing batch and semantic-break recovery

File-disjoint changes can still break semantics. For solo/local landing, schedule one main gate against the **exact landed batch tip**, with batch membership and previous green tip, after each landing batch. It is one batch check; a clean task without a carried retest obligation gets no new per-task gate; a dirty candidate's just-in-time check is separately justified above. Serialize subsequent batches in that repo until the tip's main gate is green. For the enabled W2 solo policy this post-batch check replaces the current blanket full pre-landing batch rerun; do not schedule both by default. The landing adapter must explicitly accept the prior task evidence plus clean transport receipts only where no retest obligation is pending, or matching successful retest receipts covering all carried obligations, record main health as pending, and obtain the new exact-tip main gate afterward. Pending health is never a passing gate receipt or permission to start the next landing batch. Existing independently required initial task gates remain evidence; an explicitly stricter repo pre-landing requirement still applies and is separately identified in policy/cost. Enable this path only after the receipt/state adapter and red-main hold/bisection are available together.

On red, hold further landing in that repo and use `landing.bisect` on the recorded ordered batch from the previous green baseline in isolated candidates, reserving normal heavy units for each test. Bisection tests are an explicit failure-recovery exception to the one-gate rule. Record the culprit/evidence; a preexisting red baseline or nonreproducible failure opens one owner issue rather than blaming a task without evidence. Create a bounded repair task with applicable approval (OP2/OP1 may be set under their rules), then gate the repaired main batch. Never reset published history or silently undo a landed task/decision. Team repos rely on GitHub's required PR checks and configured post-merge main check; diagnostics may bisect locally, but every remote repair/merge still requires the existing owner authority.

All classification, integration, retest and resolution steps emit E-v events with input/output SHAs, policy, elapsed time and resource/model cost. E-v measures clean/dirty/conflict rates, skipped versus repeated tests, retest CPU time and semantic breaks; it can propose policy lessons but cannot weaken team approval, gate provenance or the no-force-push rule.

For .NET stages, use an authorized platform/worker: Windows with Claude, or WSL with Claude/Codex, subject to repo `[run] platforms`. Sandbox network is unavailable. Restore only from the existing read-only `~/.nuget/packages` cache and leave `NUGET_PACKAGES` pointing there. Missing packages or denied cache reads are blockers: report the exact package/error and ask the owner to arrange an approved readable local cache. Do not install packages, change sources or try network workarounds. This spec does not authorize starting extra builds outside admission.

## Events and the self-improving harness (E-v)
