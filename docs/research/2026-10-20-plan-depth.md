# AI coding plans: depth, shape, and evidence

*Research report, 20 October 2026. I couldn’t save this as a file because the workspace is mounted read-only; the report is here.*

## Findings

The strongest common pattern is a **chain of artifacts**: describe intended behavior, make the necessary architectural decisions, then break implementation into small tasks with explicit verification. The templates differ in how far they go toward file and interface detail.

Evidence supports planning as a useful control, but not a guaranteed fix: a study of 21,120 SWE-agent trajectories found that a standard plan improved resolution, while a poor plan could perform worse than no plan; reminders improved plan adherence, and extra phases sometimes hurt. This was a benchmark study, not an evaluation of Drover’s models or parallel workflow. [Paper](https://arxiv.org/abs/2604.12147)

Practitioner reports are anecdotal and mixed. Some describe success from saving a detailed plan, starting a fresh execution session, and reviewing against the plan; others say planning is unnecessary for familiar, small changes or that excessive detail can confuse execution. [Hacker News](https://news.ycombinator.com/item?id=46354970), [r/ChatGPTCoding](https://www.reddit.com/r/ChatGPTCoding/comments/1plo81k/how_i_code_better_with_ai_using_plans/), [Lobsters](https://lobste.rs/s/6ifojq/coding_with_llms_summer_2025_update)

## Product comparison

“Documented” below means product or repository documentation, not independent validation. Where no stable template is published, I say so instead of inferring one.

- **GitHub Spec Kit — spec → plan → tasks, with a constitution.** The spec template’s headings include `User Scenarios & Testing`, `Requirements`, `Success Criteria`, and `Assumptions`; the constitution has `Core Principles` and `Governance`; the plan has `Summary`, `Technical Context`, `Constitution Check`, `Project Structure`, and `Complexity Tracking`. Tasks are grouped by setup, foundations, and user story, with dependencies and parallel opportunities. The task format calls for exact paths and marks parallel work when files differ and there are no dependencies—but tests are explicitly optional unless requested in the spec. The docs define artifacts and workflow, not a strong-planner/weak-implementer model split. [Spec](https://github.com/github/spec-kit/blob/main/templates/spec-template.md), [constitution](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md), [plan](https://github.com/github/spec-kit/blob/main/templates/plan-template.md), [tasks](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)

- **OpenSpec — proposal, behavior deltas, design, tasks, archive.** Its headings include `Why`, `What Changes`, `Capabilities`, `Impact`; design uses `Context`, `Goals / Non-Goals`, `Decisions`, and `Risks / Trade-offs`; tasks use numbered groups with checkboxes. The AI drafts artifacts and the user reviews the plan before apply; tasks should fit one session and each must state how completion is verified. The workflow archives accepted behavior deltas into the living specs. Docs leave design out when it is unnecessary; they do not prescribe model strength. [Schema and templates](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/spec-driven/index.md), [workflow](https://github.com/Fission-AI/OpenSpec/blob/main/docs/getting-started.md)

- **obra/Superpowers — brainstorm, plan, execute task by task.** Its plan header includes `Goal`, `Architecture`, `Tech Stack`, `Spec`, `Global Constraints`, and `Review Focus`; each task has `Files` and `Interfaces`. It specifies failing tests, the command and expected failure, implementation with exact signature and path, then the passing command and expected result. Its writer is expected to make the plan unambiguous for an executor with limited context; implementation follows one task at a time with checks and review. It does not prescribe a named stronger planner model. [Plan template and granularity](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md), [execution](https://github.com/obra/superpowers/blob/main/skills/executing-plans/SKILL.md)

- **AWS Kiro — requirements, design, tasks.** Its artifacts cover user stories and acceptance criteria, EARS-style requirements, edge/error cases, architecture and components, models/interfaces, testing strategy, and discrete tasks with outcomes, dependencies, and optionality. The user reviews each phase and can execute tasks individually or together. The docs describe artifact content, not fixed section headings or a strong/weak model assignment. [Requirements-first workflow](https://kiro.dev/docs/specs/feature-specs/requirements-first/), [design-first workflow](https://kiro.dev/docs/specs/feature-specs/tech-design-first/)

- **Aider — architect/editor roles, without a formal plan template.** The architect model proposes a solution; the editor model converts it into specific file-edit instructions. Users can choose different models for the roles. Aider reports an 85% pass rate on its own code-editing benchmark for o1-preview paired with DeepSeek or o1-mini; this supports role separation on that benchmark, not a general claim about planning quality. [Modes](https://aider.chat/docs/usage/modes.html), [benchmark and method](https://aider.chat/2024/09/26/architect.html)

- **Cline and Roo — planning/execution modes, without canonical plan templates.** Cline’s Plan mode gathers context, asks questions, and creates a plan without execution; Act mode has editing and command tools. Separate models can be configured per mode. Roo’s Architect mode allows reading and restricted Markdown editing; its docs also describe separate models per mode. Roo’s public repository was marked archived in May 2026, so that description refers to the documented repository snapshot. [Cline modes](https://github.com/cline/cline/blob/main/.clinerules/cline-overview.md), [Roo modes and repository status](https://github.com/RooCodeInc/Roo-Code/blob/main/apps/docs/docs/basic-usage/using-modes.md)

- **Devin — codebase-informed preliminary plan, no public fixed template.** Cognition says Devin returns relevant files and findings with a preliminary plan that users can modify. Devin 2.1 reports confidence after planning, asks questions when confidence is not green, and waits for approval when unsure. Cognition reports a correlation between green confidence and twice the likelihood of a merged PR versus red; that is a vendor-reported correlation, not causal evidence. [Devin 2.0](https://cognition.com/blog/devin-2), [Devin 2.1](https://cognition.com/blog/devin-2-1)

- **Factory Missions — feature/milestone plan with validation.** Droid collaborates on features, success criteria, milestones, and skills; the user approves the plan before execution. Model settings allow a stronger orchestrator and faster worker, a tradeoff Factory recommends for planning versus routine tasks. Factory describes validation at milestones, but also says whether parallelization improves results remains an open question. It publishes no fixed Markdown plan headings in these docs. [Overview](https://docs.factory.com/missions/overview), [planning and validation](https://docs.factory.com/missions/planning), [model settings](https://docs.factory.com/missions/reference)

- **Anthropic — guidance, not a formal plan format.** Claude Code guidance recommends exploring before planning and coding, using tests with expected inputs/outputs, and correcting course early. For long-running work, Anthropic describes an initializer that leaves requirements and progress artifacts for later coding sessions. The guidance does not prescribe planner/executor model separation. [Claude Code best practices](https://code.claude.com/docs/en/best-practices), [long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

- **BMAD — evidence-based, risk-sized planning.** Current `bmad-build` investigates the codebase and upstream planning docs; it uses a minimal plan for clear, local work and asks for approval on a fuller written plan when intent gaps, irreversible actions, or broad footprint warrant it. It builds one ticket per session and reviews the result independently. Current docs do not publish a fixed plan-heading template; its architecture spine records only non-obvious decisions that separate agents might otherwise make inconsistently. [Build a Change](https://docs.bmad-method.org/build/build-a-change/), [architecture guidance](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/plan/design-ux-and-architecture.md)

- **Taskmaster AI — structured task records, not required file-level plans.** Its task format exposes `Task ID`, `Title`, `Status`, `Dependencies`, `Priority`, `Description`, `Details`, and `Test Strategy`. An agent selects dependency-ready work and uses `details` and `testStrategy` during implementation; configuration supports separate main, research, and fallback models. The documented schema does not require exact file paths or a write-set contract. [Task format](https://github.com/eyaltoledano/claude-task-master/blob/main/docs/task-structure.md), [workflow and model configuration](https://github.com/eyaltoledano/claude-task-master/blob/main/README-task-master.md)

## What “complete enough” means

A plan is complete enough when a worker who lacks architectural context can make the intended change without inventing decisions that should have been settled upstream. It need not spell out every code body: Superpowers’ guidance is to specify exact interfaces and verification, leaving implementation bodies to the worker when those are determined by the contract and tests. [Superpowers plan guidance](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)

Use this checklist:

1. **Behavior:** observable acceptance criteria, edge/error cases, non-goals, and behavior that must not change.
2. **Repository grounding:** real paths and symbols, the existing pattern to follow, and the extension point to use.
3. **Architecture:** decisions, rationale, interfaces, ownership, data shapes, and error behavior that another worker could not safely infer.
4. **File-level scope:** create/modify/delete paths per task, each path’s purpose, and exact functions/classes or signatures where integration depends on them.
5. **Small tasks:** one independently reviewable deliverable per task, with dependencies and explicit allowed write sets.
6. **Tests and verification:** acceptance requirement mapped to a test; test-first where useful; command and expected result for each task, plus integration checks.
7. **Parallel safety:** parallelize only tasks with disjoint write sets and no dependency; serialize shared-file changes.
8. **Drift handling and simplicity:** list unresolved questions; stop and replan if a discovery changes the design; name existing helpers to reuse and justify any new layer.

These requirements combine the strongest elements of Spec Kit’s path-aware task list, OpenSpec’s per-task verification, and Superpowers’ file/interface/test detail. The study’s warning about harmful weak plans argues for reviewing plan quality before coding, rather than treating a plan’s existence as sufficient. [Spec Kit tasks](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md), [OpenSpec tasks](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/spec-driven/index.md), [plan-following study](https://arxiv.org/abs/2604.12147)

## Implications for Drover

1. Keep the existing design-intent grill, then add a separate **implementation-contract phase** that inspects the target repo and emits paths, symbols, interfaces, tests, and decisions.
2. Use a strong planner to turn repo evidence into the contract; cheaper agents can gather candidate paths and patterns, but a planner or auditor should verify those references against the code before approval. This follows the documented model-role split in Aider and Factory. [Aider](https://aider.chat/docs/usage/modes.html), [Factory model settings](https://docs.factory.com/missions/reference)
3. Make a plan preflight gate require every acceptance criterion to map to a verification step, every task to name files and dependencies, and every cross-task contract to state exact inputs and outputs.
4. Build a task conflict graph from planned write sets. Run only disjoint tasks in parallel; route shared-file tasks through one owner or serialize them.
5. Require task-sized implementation units with their own tests and checks. Do not defer task tests to a final integration pass. [OpenSpec task guidance](https://github.com/Fission-AI/OpenSpec/blob/main/docs-lab/reference/schemas/spec-driven/index.md)
6. Give each worker only its approved task brief and relevant architecture decisions; make material scope or interface changes trigger a plan update before continuing.
7. Measure first-pass CI acceptance, off-plan file edits, duplicate/new abstractions, write-set conflicts, and HOLD rounds for a pilot cohort. The research supports testing the plan process against Drover’s outcomes; it does not establish that any template will prevent 80% of issues. [Plan-following study](https://arxiv.org/abs/2604.12147)
