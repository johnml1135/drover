# Research report — Topic K: From 0-0-100 to 70-20-10

## Findings

The tools and studies support assigning repository facts and repeatable checks to scripts, using small models for calibrated triage, and keeping large models for ambiguous design choices and high-risk review. They do **not** establish 70-20-10 as a proven ratio; treat it as a Drover pilot target, measured against review misses, HOLD/fix rounds, latency, and cost. [Anthropic’s agent-evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [RouteLLM](https://github.com/lm-sys/routellm)

- **Plan sidecar and preflight.** *Proposed composition:* have the planner emit structured fields for paths to read/write/create, symbols, task dependencies, acceptance tests, commands, and expected base results. Validate the schema, paths, and symbols using JSON Schema plus Python AST, Ctags, or an available LSP workspace-symbol query. For a regression fix, run the named test against the base and require it to fail there before requiring it to pass on the patch—a pattern used by SWE-bench and recommended by practitioners. This is custom Drover glue; the building blocks are documented, but they do not judge whether the architecture is right. **Cost:** metadata checks are a low-cost engineering estimate; the base run costs test time. **False flags:** legitimate new files, renamed/re-exported symbols, dynamic definitions, flaky tests, or unrelated base failures. Replaces model checks of path/symbol existence and test-command plausibility. [JSON Schema](https://json-schema.org/docs), [Python AST](https://docs.python.org/3.12/library/ast.html), [Ctags JSON](https://docs.ctags.io/en/stable/man/ctags-json-output.5.html), [LSP workspace symbols](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.18/workspace/symbol.md), [SWE-bench grading](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py), [r/ChatGPTCoding discussion](https://www.reddit.com/r/ChatGPTCoding/comments/1wi1wxd/how_are_you_catching_agent_tests_that_pass_on_the/)

- **Write-set guard and collision check.** Compare the actual diff paths with the approved sidecar and fail on undeclared paths; compare agent write sets before dispatch and serialize overlapping tasks. Policy-bot supports pull-request rules based on changed, added, and deleted files, and Danger runs project-authored CI rules over PR metadata. **Cost:** a path comparison is a low-cost engineering estimate. **False flags:** legitimate discoveries such as required config or generated files; require a plan amendment to expand the set. Replaces model rereads for scope compliance and surfaces parallel collisions before edits begin. [Policy-bot file predicates](https://github.com/palantir/policy-bot), [Danger JS](https://danger.systems/js/)

- **Test integrity and behavior deletion.** Preserve hashes or a collected-ID manifest for trusted baseline tests and runner configuration; permit new tests, while flagging deletions, skips, or edits to protected tests for review. For Python public API removals, Griffe can compare versions; coverage.py records branches and per-test contexts. A custom base-versus-candidate comparison can identify deleted behavior exercised by existing tests. `diff-cover` measures coverage on changed lines, but its docs warn that some multiline statements are missed; it does not by itself show coverage of deleted lines. **Cost:** hashes and API diffs are cheap; coverage requires test runs. **False flags:** intentional test/API refactors; **misses:** untested behavior and weakened assertions outside the protected set. Replaces LLM scans for deleted APIs, tests, and review claims that relevant tests ran. [pytest collection](https://docs.pytest.org/en/stable/how-to/usage.html), [Griffe API checks](https://mkdocstrings.github.io/griffe/reference/api/), [coverage.py contexts](https://coverage.readthedocs.io/en/latest/contexts.html), [branch coverage](https://coverage.readthedocs.io/en/6.5.0/branch.html), [diff-cover limitations](https://github.com/newbery/diff-cover)

- **Changed-code mutation testing.** Mutmut supports incremental results, test selection, function-level runs, and coverage-based line filtering; Cosmic Ray runs tests against code mutations and can distribute work. Neither should be assumed to provide an exact changed-lines-only PR gate out of the box: map changed hunks to functions or add a narrow selector. **Cost:** high relative to static gates, scaling with mutants and relevant test time. **False signals:** survivors may be equivalent or low-value mutations; unstable tests can distort results. Use a small budget on critical changed logic. This replaces a model’s guess about whether tests would notice altered behavior; it does not validate the feature’s intent. A practitioner thread with the mutmut author describes runs taking an hour and recommends limiting scope. [mutmut docs](https://mutmut.readthedocs.io/en/latest/index.html), [Cosmic Ray](https://cosmic-ray.readthedocs.io/en/stable/index.html), [Google Research on mutation testing at scale](https://arxiv.org/abs/2102.11378), [Hacker News discussion](https://news.ycombinator.com/item?id=39850087)

- **Architecture rules.** Import Linter enforces forbidden imports, layers, independence, and cycles; Grimp builds the import graph; Semgrep can enforce repo-specific code patterns. These checks are cheap static analysis once contracts are defined. **False flags:** stale or broad rules and legitimate exceptions; **misses:** dynamic imports or design problems that were never encoded as rules. Replaces repeated review of explicit dependency and pattern rules; it does not select the architecture. [Import Linter contracts](https://import-linter.readthedocs.io/en/stable/contract_types/), [Grimp](https://grimp.readthedocs.io/en/stable/usage.html), [Semgrep rule-writing methodology](https://semgrep.dev/blog/2020/writing-semgrep-rules-a-methodology/)

- **SWE-bench-style test harness.** Record `FAIL_TO_PASS` tests that should fail on base and pass after the change, plus `PASS_TO_PASS` tests that must remain green. This gives a deterministic result for behavior covered by those tests, at the cost of running them. **False flags:** flaky tests, bad baseline statuses, and tests that reject valid implementations. A later OpenAI audit of 138 difficult SWE-bench Verified instances found material test or description issues in 59.4%, so validate Drover’s own oracle rather than treating the pattern as infallible. Replaces model interpretation of test outcomes and regression claims. [SWE-bench harness](https://www.swebench.com/SWE-bench/api/harness/), [OpenAI audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

- **Danger and policy bots.** Danger codifies routine review conventions; Policy-bot applies approval rules based on PR files, authors, or branches. **Cost:** low script/API overhead. **False flags:** stale or brittle rules. These tools check policy and metadata, not semantic correctness, so they replace checklist review rather than code review. [Danger JS](https://danger.systems/js/), [Policy-bot](https://github.com/palantir/policy-bot)

- **Small-model judging and routing.** Use a rubric-based small model for subjective checks that remain after scripts—such as criterion-to-diff alignment—and require criterion-specific evidence and abstention when uncertain. Anthropic recommends calibrating LLM graders against human experts; ACL 2026’s CodeJudgeBench found small reasoning judges could beat larger non-reasoning judges, but all tested judges were sensitive to answer order, variable names, and misleading comments. RouteLLM and FrugalGPT show cost/quality tradeoffs and cascades, but their benchmarks do not establish equivalent savings for coding-agent review; calibrate on Drover tasks. **False flags:** inconsistent judgments; **routing risk:** an easy route can under-review a hard task, while escalation costs more. Replaces the first large-model whole-diff pass; keep large-model review for high-risk or unresolved cases. [Anthropic evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [CodeJudgeBench](https://aclanthology.org/2026.acl-long.888/), [RouteLLM](https://github.com/lm-sys/routellm), [FrugalGPT](https://arxiv.org/abs/2305.05176)

**Practitioner signal, anecdotal:** one r/ClaudeAI reviewer says a small model handles most code-review investigations faster, but roughly one in ten is “way off”; another says it performs better on targeted edits with supplied files. This favors bounded small-model review with escalation. [r/ClaudeAI discussion](https://www.reddit.com/r/ClaudeAI/comments/1ow5lk0/what_are_your_thoughts_on_haiku_45/)

## Implications for Drover

1. Make every plan produce a sidecar with repo SHA, acceptance criteria, exact write/create sets, symbols, test IDs/commands, expected base results, and architecture constraints; validate it before dispatch.
2. Keep approved write sets outside the agent-editable workspace; block undeclared diff paths and serialize tasks whose write sets intersect.
3. Protect a baseline test oracle and runner config. Allow new tests, but require review for changes to protected tests, collection, skip settings, or test commands.
4. At each task handoff, run baseline-aware acceptance and regression checks; report exact commands, exit codes, changed files, and unverified checks.
5. Encode current architecture boundaries with Import Linter and targeted Semgrep rules; review exceptions as architecture changes.
6. Run mutation checks on selected changed functions in critical logic; keep broader mutation runs periodic until runtime justifies wider CI use.
7. Calibrate a small-model rubric on Drover’s prior HOLD/fix examples; require file/line evidence, and escalate ambiguous or high-risk findings to a large model.
8. Track the 70-20-10 split by decision count and spend, then tune it against escaped issues and review rounds; keep large-model calls for architecture decisions, ambiguity, and unresolved risk.
