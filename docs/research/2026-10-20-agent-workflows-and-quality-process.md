# Topic C: Multi-Agent AI Workflows and Quality Processes

## Finding

There is no evidence that any workflow reliably prevents 80% of issues in Drover’s setting. Treat that figure as a target to measure against Drover’s own baseline. The best-supported approach is to make implementation plans specific enough to review before coding, encode architecture rules as fast CI checks, and split parallel work around stable module boundaries. That directly addresses vague plans, architectural drift, and file conflicts; it cannot remove ambiguity or guarantee correct behavior. ([Anthropic’s long-running-agent study](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [OpenAI’s harness report](https://openai.com/index/harness-engineering/), [failed-agent-PR study](https://arxiv.org/abs/2601.15195))

## What the workflows show

| Workflow | Documented pattern and practical lesson |
|---|---|
| **Gas Town and Beads** | Gas Town separates coordination and execution roles: the Mayor starts work, Polecats implement, Witnesses monitor workers, the Deacon supervises, and the Refinery processes a merge queue. Convoys track batches of work; Beads supplies persistent, dependency-linked tasks. Yegge also describes duplicate fixes, lost work, and designs needing to be redone; he says oversized tasks can overwhelm Polecats. This is useful machinery for tracking and merging work, but it does not itself ensure sound decomposition or architecture. ([Yegge’s Gas Town post](https://yegge.ai/essays/welcome-to-gas-town/), [Gas Town repository](https://github.com/gastownhall/gastown), [Beads repository](https://github.com/gastownhall/beads), [Yegge on task size and stability](https://steve-yegge.medium.com/steveys-birthday-blog-34f437139cb5)) |
| **Claude Code** | Subagents provide focused work in separate contexts; agent teams add direct messaging and a shared dependency-aware task list. Anthropic advises using teams for independent tasks, warns that same-file edits overwrite each other, and says teams cost more tokens and add coordination overhead. Agent teams are documented as experimental. ([subagent docs](https://code.claude.com/docs/en/sub-agents), [agent-team docs](https://code.claude.com/docs/en/agent-teams)) |
| **OpenHands, MetaGPT, ChatDev** | OpenHands provides composable agent and workspace building blocks. MetaGPT encodes software roles and SOPs into structured intermediate artifacts; ChatDev uses role-based dialogue and communication chains. These papers motivate staged work and explicit handoffs, but benchmark or framework descriptions do not establish production reliability. ([OpenHands SDK](https://docs.openhands.dev/sdk), [MetaGPT paper](https://arxiv.org/abs/2308.00352), [ChatDev paper](https://arxiv.org/abs/2307.07924)) |
| **Sweep, Factory, Cursor, Amp** | Sweep documented a particularly relevant step: translate an issue into file-level instructions before editing, then feed CI failures back to the agent. Factory droids package focused prompts, model choices, and tool policies. Cursor worktrees isolate agents’ checkouts; Amp gives each thread its own working copy and says to use one thread per task. These patterns help constrain work, but isolation does not prevent separate agents from making incompatible design assumptions. ([Sweep planning](https://github.com/sweepai/sweep/blob/main/docs/pages/blogs/ai-code-planning.mdx), [Sweep CI feedback](https://github.com/sweepai/sweep/blob/main/docs/pages/blogs/giving-dev-tools.mdx), [Factory subagents](https://docs.factory.com/harness/subagents), [Cursor worktrees](https://prod.cursor.com/docs/configuration/worktrees), [Amp agent-to-agent](https://ampcode.com/docs/orbs/agent-to-agent)) |

## What practitioners and published guidance report

A study of 33,000 agent-authored PRs found that documentation, CI, and build updates merged most often, while performance and bug-fix tasks did worst. Unmerged PRs tended to be larger, touch more files, and fail CI; reviewers also rejected duplicate, unwanted, or misaligned work. This points to scope, task fit, verification, and review engagement as pipeline problems alongside code correctness. ([MSR 2026 study](https://arxiv.org/abs/2601.15195))

Practitioner reports echo the coordination issue: worktrees prevent simultaneous edits to one checkout, but do not prevent conflicting plans or incompatible assumptions. People report better results when they declare expected files up front, divide work by module or layer, and avoid parallelizing shared schemas, types, and migrations. Treat these as useful anecdotes, not controlled evidence. ([r/ClaudeAI on worktrees and scope](https://www.reddit.com/r/ClaudeAI/comments/1t9tolw/running_two_claude_code_agents_on_the_same_repo/), [r/ClaudeCode on module-level decomposition](https://www.reddit.com/r/ClaudeCode/comments/1sr2ni6/how_are_you_guys_managing_multiple_ai_coding/), [Gas Town discussion on sequencing](https://github.com/gastownhall/gastown/discussions/1213))

Anthropic reports that long-running agents often try to do too much at once, lose track of unfinished work, or declare completion prematurely. Its tested countermeasures were an initializer that creates a runnable environment and structured feature list, followed by sessions that implement one feature, test it, and leave a clean state and progress record. Anthropic also found that vague delegation produced duplicate work and gaps in its multi-agent research system; it recommends clear task boundaries, outputs, and effort budgets. ([long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [multi-agent system lessons](https://www.anthropic.com/engineering/multi-agent-research-system))

OpenAI reports that its team moved from cleanup of “AI slop” to enforcing architectural invariants mechanically with linters and structural tests. That is a company’s account of its own system, not a general comparative study, but it directly supports putting architecture rules into tools instead of relying on prose alone. ([OpenAI harness engineering](https://openai.com/index/harness-engineering/))

## Traditional quality methods that transfer

PSP/TSP track where defects are introduced and found, measure phase yield, and use design and code reviews to improve the process. One SEI-published TSP classroom example reported 84% process yield before unit test; that is evidence that an early-yield target can be measured, not a forecast for Drover. Fagan’s formal design and code inspections likewise use defined roles and defect data to improve inspection effectiveness. ([SEI on PSP](https://sei.cmu.edu/library/the-personal-software-process-psp/), [SEI TSP example](https://www.sei.cmu.edu/documents/1447/2010_021_001_298903.pdf), [Fagan paper](https://doi.org/10.1147/sj.153.0182))

Toyota’s **jidoka** principle is to stop work when an abnormality appears, preventing defects from flowing downstream. In Drover, the equivalent is blocking an agent’s next stage when its architecture check, tests, or task contract fails, then recording the cause and fixing the guardrail. **Cleanroom** adds incremental implementation, correctness verification, and statistically grounded testing; use those ideas selectively for high-risk changes rather than imposing the full formal process on routine tasks. ([Toyota Production System](https://global.toyota/en/company/vision-and-philosophy/production-system/), [SEI Cleanroom reference](https://insights.sei.cmu.edu/documents/1159/1996_005_001_16502.pdf))

Cost-of-defect figures need care: NIST’s often-cited 1×/5×/10×/15×/30× progression is explicitly an **example**, not a universal law. It supports finding defects early, but Drover should measure its own rework cost and escape rate. ([NIST report](https://www.nist.gov/document/report02-3pdf))

## Implications for Drover

1. **Add a pre-implementation contract gate.** Require each task plan to name files and symbols to change, intended edits, current patterns to reuse, interface changes, dependency direction, invariants, acceptance tests, and non-goals. Review this before dispatch; “use X and fix Y” is not an implementation plan.
2. **Give agents an architecture map.** Keep a short repository index pointing to current module responsibilities, approved extension points, canonical examples, and architecture decisions. Treat it as a map to maintained sources, not a giant instruction manual. ([OpenAI’s repo-knowledge approach](https://openai.com/index/harness-engineering/))
3. **Make architecture conformance a cheap hard gate.** Add `import-linter` contracts for forbidden imports, layers, and independent packages to CI; use custom structural checks where rules need more context. These checks catch dependency violations deterministically and can run before expensive review. ([Import Linter contract types](https://import-linter.readthedocs.io/en/v1.9.0/contract_types.html), [ArchUnit guide](https://www.archunit.org/userguide/html/000_Index.html))
4. **Gate parallelism on a task graph and ownership.** Declare dependencies and expected file/module ownership before dispatch. If tasks overlap on a shared type, schema, migration, or interface, land that foundation first or serialize the work; give each agent an isolated worktree. ([Claude team best practices](https://code.claude.com/docs/en/agent-teams), [Beads dependency model](https://github.com/gastownhall/beads))
5. **Ship small vertical slices with proof.** Have each implementer complete one bounded change, run the relevant tests and architecture checks, and report commands and results. Require a clean state and progress record at handoff. Don’t treat the agent’s “tests pass” as evidence without captured output. ([Anthropic long-running harness guidance](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))
6. **Move review earlier and stop on failure.** Review the implementation contract before coding and the first meaningful diff before broad implementation continues. On a failed test, architecture rule, or scope check, stop dependent work, classify the defect, and use the finding to improve the contract or gate.
7. **Measure the 80% goal.** Track HOLD/rework causes, defect origin and detection stage, overlapping-file conflicts, first-pass acceptance, and review rounds. Set “80% fewer preventable scope, architecture, and coordination issues” against Drover’s measured baseline; don’t infer success from throughput or PR count. ([PSP/TSP quality measures](https://sei.cmu.edu/library/the-personal-software-process-psp/), [failed-agent-PR study](https://arxiv.org/abs/2601.15195))
