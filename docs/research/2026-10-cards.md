# Dense task cards — research, 2026-10-19

## 1 / 4 — Evidence and current Drover

**Brief:** about four text lines per collapsed card; 5–10 items visible; title/states on phones, tap for full detail; a grip replaces prominent Move up/down buttons. Findings below are documentation research, not authenticated product trials or measured screenshots. Layouts and dimensions are proposals.

| Reference | Density / disclosure pattern worth borrowing |

**Why 1–2:** [app.css](../../hub/static/app.css) uses a 60rem content cap, 16px/1.45 text, paragraph margins, nested padding, wrapping badges and 44px action controls. `first_paragraph()` in [task_views.py](../../hub/task_views.py) limits paragraphs, not lines; `.description-preview` has no clamp. Thus information stacks vertically while desktop width goes unused; this is content-dependent, not a fixed two-card limit.

## 2 / 4 — Four candidate layouts

Examples are illustrative, not live task state. `::` = reorder grip; `>`/`v` = disclosure; `...` = more. Desktop sketches abbreviate text; phone sketches show the collapsed row and what tapping reveals. Full detail always includes the fields on page 3.

**A. Three-column card — recommended desktop default.** Identity/metadata, description, things to do; four visual lines high, not four lines in each column stacked vertically. Useful for comparing intent and owner action; needs roughly 1100px of usable width. Below that, use B, then phone rows.

```text
Desktop: ~1280px content                              Phone: ~390px
+-------------------+------------------+------------+ +-------------------------+
|:: T42 Cards       | Research dense   | Next: review| |> T42 Cards            |
|drover Hub research| work-item views  | AC: 3      | |P1 research needs-owner  |
|P1 needs-owner     | across tools...  | R1 L2      | +-------------------------+
|Waiting on: owner  | [Expand]         | [Review] ...| |tap -> full stacked card |
+-------------------+------------------+------------+ |description/AC/next/runs  |
                                                      +-------------------------+
```

**B. Four-line accordion.** Best at intermediate widths and for Inbox review; one selected item expands inline. Simpler reading order, but expanded content pushes neighboring items away.

```text
Desktop: ~960px content                               Phone: ~390px
+--------------------------------------------------+ +-------------------------+
|:: > T42 Cards                              [...] | |> T42 Cards            |
|drover / Hub epic / research / P1 / needs-owner     | |P1 needs-owner           |
|Research dense work-item views across tools...     | +-------------------------+
|Waiting on: owner                 Next: review     | |tap: v T42        [Close]|
+--------------------------------------------------+ |full description + AC    |
|v expands: full description, AC, actions, runs/links| |Next: review; runs/links |
+--------------------------------------------------+ +-------------------------+
```

**C. Dense table + selected-item peek.** Best for backlog/landing triage and comparing state/repo/priority. Description and acceptance live in the adjacent pane; preserves list position. Higher density sacrifices per-item narrative.

```text
Desktop: ~1280px content                              Phone: ~390px
+-----------------------------+--------------------+ +-------------------------+
|  Title       Repo  P State   |T42 Cards    [Close]| |> T42 Cards            |
|::T42 Cards   drover 1 owner  |Waiting on: owner   | |P1 needs-owner           |
|::T43 Tests   drover 2 ready  |Description         | +-------------------------+
|::T44 Docs    other  2 running|AC / Next: review   | |tap -> full-height detail|
| ...                         |Runs / links        | |[Back] T42; full fields  |
+-----------------------------+--------------------+ +-------------------------+
```

**D. Compact workflow board.** Best for bottlenecks; two visible state columns with four-line cards. Uneven queues reduce useful density; poor for comparing prose across many states. Phone selects one state rather than shrinking columns.

```text
Desktop: ~1280px content                              Phone: ~390px
+------------------------+-------------------------+ +-------------------------+
|Ready (8)               |Needs owner (3)          | |State: Needs owner (3) v |
|:: T43 Tests            |:: T42 Cards             | |> T42 Cards            |
|drover Hub / fix / P2   |drover Hub / research P1 | |P1 needs-owner           |
|Test reorder behavior  |Research dense views...  | +-------------------------+
|Next: run; R0 L1        |Waiting on: owner R1 L2  | |tap -> full card / Close |
+------------------------+-------------------------+ +-------------------------+
```

## 3 / 4 — Fields, density and recommendation

Model evidence: [schema](../../drover/ledger/schema.py), [decoding/holds](../../drover/ledger/ops.py), [projections](../../hub/store.py), [grouping](../../hub/web.py). “Type” is `kind`; `description` aliases `goal`.

| Field / actual source | Collapsed A / B / C / D; full detail |
|---|---|
| Title + ID: `title`, `id` | Visible/linked everywhere; full title on expansion. |
| Repo, epic: `repo`, `epic_id` → epic title | A/B metadata; C columns; D metadata/group header. Full names in detail; omit repeated grouping labels. |
| Type, priority: `kind`, `priority` | A/B/D metadata; C configurable columns. Phone prioritizes priority/state, type if room. |
| State: `status` (`state` alias) | Always text. A/B/D reason line; C secondary line. Phone attention reason replaces secondary metadata. |
| Waiting on / Stuck banner (T-cu) | Reserve reason line everywhere; full cause/action in detail. T-cu is absent here: consume its eventual contract. Current sources: `blocker` holds/reasons, dependencies and status-event reasons. Never infer “Stuck” from age alone. |
| Description: `goal` / `description` | A middle column ≤3 lines; B one preview line; C peek; D one line. Full Markdown in detail. |
| Acceptance: `acceptance[]` | A count/first criterion; B/C/D expansion/peek. Full criteria in detail. No completion flags: counts are not progress. |
| Next actions | No structured `next_actions`. A third column; B/D short step; C peek. Derive eligible owner controls (e.g. Accept findings) from workflow; free-text `handoff` is not an action list. |
| Runs: `runs` rows by task ID | A/D count/latest outcome; optional B/C summary; full linked history in detail. Requires list projection enrichment. |
| Links: dependencies, dependents, `task_links`; Markdown URLs | A/D counts, optional B/C; full labeled links in detail. No external-links field. Branch/worktree, scope, access, events stay in detail. |

**Density budget (estimates):** assume 1920×1080 physical pixels at 100% OS/browser scale; subtract 80px browser chrome, 160px app header/navigation/filters and 40px group header: **800 CSS px for items**. Count complete items with `floor(800 / pitch)`. Pitch includes padding, borders and inter-item gap. More groups, wrapping, zoom and expansion reduce counts.

| Layout | Height budget / pitch | Complete items per screen |
|---|---|---|
| Current long Plan/Inbox card | Estimated 400–650px: repeated metadata/controls plus 4–8 description lines and reasons | **1–2**; not browser-measured |
| A / B collapsed | 4×20px lines + 16px padding + 2px borders + 8px gap = **106px** | **7**; a fifth 20px reason/title line gives **6** |
| C table + side peek | **44–64px** rows; reserve 40px table header | **11–17** scan rows; optional comfortable density can target 8–10 |
| D board | **130px** pitch; reserve 40px column header | **5 per column**, 10 across two; only 5 if all work occupies one |

Phone assumption: 390×844 CSS viewport minus 220px app/browser/bottom controls = 624px; 72–88px collapsed rows yield **7–8**. At 200% desktop zoom, rerun with the smaller CSS viewport; never enforce counts by clipping text or shrinking targets.

**Recommendation:** A for wide Plan/Inbox (requires widening today's 60rem cap), B at intermediate widths, phone rows opening a stacked full card. Keep T-cu reasons visible; one contextual action plus overflow. Offer C for scanning, especially landing/backlog; defer D. Preserve `/tasks/{id}` for full detail. Roadmap planning dates are absent from today’s model; defer that view too.

## 4 / 4 — Interaction guidance and owner questions

**Density and mobile disclosure.** [Material 3 lists](https://m3.material.io/components/lists/overview) use headline/supporting/trailing content and 56/72/88dp item heights; these are native references, not mandatory web pixels. [M3 typography](https://m3.material.io/styles/typography/applying-type) favors readable body spacing. Apple HIG favors scannable, reorderable rows, [progressive disclosure](https://developer.apple.com/design/human-interface-guidelines/layout), and [selection feedback](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables?changes=_5). Our adaptation: distinct disclosure and grip controls in a reserved slot; neither guide prescribes a four-line task card. Choose fields before reducing type.

Phone alternatives: inline expansion preserves context but moves rows; a [bottom sheet](https://developer.apple.com/design/human-interface-guidelines/sheets?changes=_1_1) supports quick reading/actions with a visible Close control; a full detail page suits long descriptions/editing. [Split views](https://developer.apple.com/design/human-interface-guidelines/split-views?changes=_6) suit wide screens; narrow phones should navigate between list and detail. Recommendation: tap opens full card, Back/Close restores row focus and scroll; use a short sheet for quick decisions/comments, avoiding nested sheets.

**No-framework implementation options (future work only):**

| Concern | Options and preferred fit |
|---|---|
| Clamp | CSS `line-clamp` plus `display:-webkit-box; -webkit-box-orient:vertical; -webkit-line-clamp:N; overflow:hidden` compatibility path. Apply to plain preview text, not interactive controls or whole rich Markdown. Unprefixed support remains limited; fallback to a bounded preview with explicit “Expand.” [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/line-clamp). |
| Expand/collapse | Native `details`/`summary` needs no JS; keep independent links/actions outside the summary. Alternatively a small delegated JS listener toggles a class/`hidden` and button `aria-expanded`/`aria-controls`. Hide inactive duplicate detail from focus/AT; CSS clipping alone does not do that. [Native disclosure](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details), [ARIA disclosure](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/). |
| htmx | Lazy GET a detail fragment on explicit expansion; POST actions/reorder; server renders HTML. htmx handles transport/swaps, not clamping or drag gestures. Preserve open task IDs, focus, scroll and drafts across swaps. Its [sortable example](https://htmx.org/examples/sortable/) integrates SortableJS and disables sorting during requests. |
| Drag handle | Prefer existing vendored SortableJS `handle` option; no install/framework. Pure JS could use [HTML drag events](https://developer.mozilla.org/en-US/docs/Web/API/HTML_Drag_and_Drop_API), or [Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events) for touch/pen/mouse, but custom hit-testing, cancellation and auto-scroll add work. [Sortable docs](https://github.com/SortableJS/Sortable#handle-option). |

[app.js](../../hub/static/app.js) already restricts sorting to grips, uses touch delay, persists neighbor IDs through `/plan/reorder`, pauses refresh while dragging/editing and restores group disclosure. Extend those mechanisms to individual cards. Reordering currently applies only to unfiltered epic grouping; preserve that boundary unless explicitly redesigned.

**Accessible reorder:** interpret “anchor to drag” as a visual grip implemented as a named button, not a navigation link. Apple supports keyboard/assistive [drag interactions](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop?changes=_3); GitLab’s [handle guidance](https://design.gitlab.com/patterns/drag-and-drop/) stresses focus, announcements and unobstructed mobile scrolling. Use list/article semantics; rich cards with links/buttons should not become listbox options.

Click/Enter on the grip can reveal Move up/down controls; they remain keyboard- and tap-operable without occupying every collapsed card. Optionally add scoped Alt+Up/Down shortcuts, as in [WAI’s reorder example](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/examples/listbox-rearrangeable/), retaining focus and announcing “T42 moved to position 3 of 9” via `role="status"`. Avoid deprecated [aria-grabbed](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-grabbed)/[aria-dropeffect](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-dropeffect). Provide visible focus, boundary-disabled controls and failure rollback; if using pickup mode, Space/Enter picks up/drops and Escape cancels. Keyboard alone is insufficient: [WCAG 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) also requires a non-drag pointer alternative. Keep generous phone targets and test keyboard, touch, screen reader and zoom before implementation acceptance.
